# SmartReturn Pro 핵심 제작 원칙

이 문서는 SmartReturn Pro 신규 제작 기준이다. 기존 SmartReturn의 구현기록, 화면, DB, 업무 흐름은 참고자료일 뿐이며 그대로 따르거나 복사하지 않는다.

## 신규 제작 원칙

- SmartReturn Pro는 3PL 고객사 관리 통합 플랫폼으로 확장 가능한 구조를 목표로 한다.
- OMS, WMS, RETURN, 재고, 정산, 고객사 포털은 하나의 기준 위에서 단계적으로 확장한다.
- 업무 기준, DB 기준, 공통 UI 기준을 먼저 세우고 화면과 기능 구현은 그 다음에 진행한다.
- 내부 운영자와 고객사 사용자는 `role` 기준으로 구분한다.
- 모든 업무 데이터는 `client_id` scope를 지키고, 창고 업무는 `warehouse_id` scope를 함께 지킨다.

## 기존 SmartReturn 복사 금지

- 기존 SmartReturn의 화면 구조, DB 구조, 구현 편의 로직을 그대로 가져오지 않는다.
- 기존 문서에 영어가 섞여 있어도 Pro 신규 문서는 한글 기준으로 다시 작성한다.
- 기존 기능이 동작한다는 이유만으로 Pro 기준이 되지 않는다.
- 참고가 필요한 경우에도 목적, 데이터 경계, 화면 책임을 다시 정의한다.

## 설계 우선 원칙

- 화면 먼저 만들지 않는다.
- 공통 UI, DB 원장, 업무 흐름, 권한 기준을 먼저 정한다.
- 화면은 이미 정의된 기준을 표현하는 수단이며 기준 자체가 아니다.
- 구현 중 기준이 비어 있으면 임시 구현으로 넘어가지 않고 문서를 먼저 보완한다.

## 화면 원칙

- 화면 1개는 업무 목적 1개만 가진다.
- 한 화면에 업로드, 조회, 이력, 처리, 판정, 정산, 설정을 섞지 않는다.
- 화면 이름이 비슷해도 사용자 목적이 다르면 화면을 분리한다.
- 샘플 디자인은 색상이나 느낌만 흉내 내지 않고 페이지 템플릿과 레이아웃 계약으로 강제한다.

## 공통 컴포넌트 원칙

- 공통 컴포넌트 없이 화면을 구현하지 않는다.
- AG Grid를 직접 사용하지 않고 `SmartDataGrid` 또는 `SmartEditableDataGrid` 같은 공통 래퍼를 사용한다.
- 고객사, 상품, 창고, 공통코드 선택은 화면별 Select가 아니라 공통 lookup 기준을 따른다.
- 공통모달은 크기, footer, 버튼 위치, 입력 폭을 통일한다.

## DB와 원장 원칙

- DB 원장, 업무 테이블, 로그 테이블을 분리한다.
- 업로드/import job과 실제 업무 테이블을 분리한다.
- `batch_id`는 원본 추적과 이력 확인을 위한 보조키이며 업무 처리 중심키가 아니다.
- `inventory_events`는 재고 원장이고 `current_inventory`는 현재고 요약이다.
- `scan_events`는 스캔 이벤트 로그이며 재고 원장이 아니다.
- 재고 변경은 서버의 업무 확정 흐름에서만 발생한다.

## 업무 처리 순서 원칙

- 반품은 접수/예정자료 준비, 실제 스캔/판정, 마감, 반출, 추적으로 나눈다.
- 입고는 자료 준비, 검수, 확정, 재고 반영을 분리한다.
- 출고는 자료 준비, 검수, 확정, 재고 차감을 분리한다.
- 재고는 이벤트 원장에 먼저 기록하고 현재고 요약은 그 결과로 관리한다.
- 정산은 초기에는 업무 결과를 기반으로 한 최소 기준만 두고 고도화는 후순위로 둔다.

## 초기 제외 범위

- ERP 실제 API 직접 전송
- Local Agent 자동 업데이트
- 원격 설정 강제 변경
- 고객사 포털 전체 구현
- 정산 고도화
- AI 도우미
