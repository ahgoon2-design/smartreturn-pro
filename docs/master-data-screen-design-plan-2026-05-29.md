# 기준정보 화면 디자인 및 고객사 종속 창고 정책 계획

## 1. 문서 목적

이 문서는 SmartReturn Pro 기준정보 화면을 구현하기 전에 화면 범위, 공통 디자인 패턴, 창고 정책을 확정하기 위한 계획 문서다.

기준정보 화면은 고객사, 창고, 상품, 상품바코드, 공통코드가 이후 입고, 출고, 반품, 재고, 정산의 기준이 되는 영역이다. 따라서 화면마다 제각각 구현하지 않고 `SmartDataGrid`, 공통 상세 패턴, 공통 모달, 공통 액션 기준을 먼저 맞춘다.

이 문서는 화면 구현, backend API 수정, DB schema 변경, migration, seed 변경을 포함하지 않는다. 현재 모델/API 구조와 정책 간 차이가 있으면 “후속 검토 필요”로 기록한다.

## 2. 기준정보 1차 화면 범위

기준정보 1차 화면은 아래 세 묶음으로 시작한다.

| 화면 | 1차 포함 범위 | 비고 |
| --- | --- | --- |
| 고객사 관리 | 고객사 기본정보, 고객사 소속 창고 등록, 기본 입고창고, 기본 출고창고, 기본 반품양품창고, 기본 보류창고, 기본 리퍼창고, 기본 제조사반품창고 | 창고는 고객사 상세 안에서 함께 관리한다. |
| 상품 관리 | 고객사별 상품, 상품 기본정보, 상품 바코드 | 상품 바코드는 상품 상세의 하위 목록으로 우선 처리한다. |
| 공통코드 관리 | 창고유형, 바코드유형, 반품판정, 반품사유, 보류사유, 택배사, 재고상태, 기타 운영 코드 | 코드그룹 목록 + 코드 목록 2단 구조를 우선 검토한다. |

1차에서 제외하는 화면은 아래와 같다.

- 전역 창고마스터 단독 화면
- 고객사별 창고설정 단독 화면
- 역할/권한 관리 화면
- 사용자 관리 화면
- 정산 기준정보 화면
- 반품 라벨/라우팅 정책 전용 화면

제외 항목은 후속 확장 후보로 남긴다. 특히 역할/권한, 사용자, 정산 기준정보는 업무 흐름이 안정된 뒤 별도 범위로 설계한다.

## 3. 고객사 종속 창고 정책

SmartReturn Pro에서 창고는 전역 창고마스터가 아니라 고객사 종속 기준정보로 본다.

정책 기준은 아래와 같다.

- 창고명은 같아도 `client_id`가 다르면 다른 창고다.
- 예: 이에스피마케팅-온라인창고, 이에스피마케팅-공구창고, A업체-온라인창고는 서로 다른 창고다.
- 고객사 하나에 창고는 둘 이상 존재할 수 있다.
- 입고, 출고, 반품양품입고, 보류, 리퍼, 제조사반품, 재고조회는 `client_id + warehouse_id` 기준으로 움직인다.
- 전역 창고마스터를 만들고 고객사별로 다시 연결하는 구조는 1차 화면 정책에서는 사용하지 않는다.
- 고객사 등록/상세 화면 안에서 고객사 소속 창고를 등록, 수정, 사용중지한다.
- 고객사 상세 안에서 기본 입고, 출고, 반품양품, 보류, 리퍼, 제조사반품 창고를 설정한다.
- “전체 창고”는 실제 `warehouse` row가 아니라 조회 옵션이다. DB에 전체창고를 만들지 않는다.

후속 backend 점검에서는 현재 `warehouses` 모델이 이 정책을 직접 표현하는지 반드시 확인해야 한다. 현재 확인 기준으로는 `warehouses` 테이블 자체에 `client_id`가 없고, `client_warehouse_settings`가 `client_id`, `warehouse_id`, `usage_type`, `is_default`, `active_yn`으로 고객사-창고 사용 관계를 표현한다. 이 구조는 “전역 창고 + 고객사 연결”에 가깝기 때문에, 고객사 종속 창고 정책과 맞추려면 migration 또는 리팩토링 필요 여부를 별도 검토해야 한다.

## 4. 이카운트 ERP 참고 기준

이카운트 ERP의 창고 운영 방식은 “창고별 재고 조회”, “창고 선택 조회”, “창고 미선택 시 전체 창고 조회” 흐름을 참고한다.

다만 SmartReturn Pro는 3PL 구조이므로 이카운트의 회사 기준 창고 개념을 그대로 복사하지 않는다. SmartReturn Pro에서는 고객사별 창고가 재고 수불 단위다.

운영 기준은 아래와 같다.

- 내부 운영자는 권한 범위 내에서 고객사를 선택하고, 해당 고객사의 전체 창고 또는 특정 창고 재고를 조회한다.
- 고객사 사용자는 자기 `client_id`의 창고와 재고만 조회한다.
- 창고 선택 목록도 선택된 `client_id` 또는 로그인 고객사 기준으로만 나온다.
- 창고 미선택은 “전체 창고 조회” 옵션이며 실제 창고 row가 아니다.
- 창고 선택 시 서버는 선택 창고가 resolved `client_id`에 속하는지 검증해야 한다.

## 5. 고객사용 플랫폼 확장 기준

향후 고객사용 플랫폼에서는 고객사 사용자 scope가 화면과 API에서 모두 강제되어야 한다.

- 고객사 사용자는 자기 고객사의 창고만 볼 수 있다.
- 고객사 사용자는 다른 고객사의 `warehouse_id`를 직접 넣어도 조회할 수 없어야 한다.
- 고객사 사용자가 재고 조회에서 창고를 선택하지 않으면 자기 고객사의 전체 창고 재고를 조회한다.
- 고객사 사용자가 창고를 선택하면 선택한 자기 고객사 창고의 재고만 조회한다.
- 내부 사용자는 role/permission에 따라 고객사를 선택할 수 있다.
- 내부 사용자는 선택한 고객사의 전체 창고 또는 특정 창고 재고를 조회할 수 있다.
- 모든 `warehouse_id` 입력 API는 `warehouse.client_id`와 resolved `client_id` 일치 여부를 서버에서 검증해야 한다.

현재 backend에 `warehouse.client_id`가 직접 없으므로, 현 구조를 유지한다면 `client_warehouse_settings` 또는 별도 고객사-창고 소유 정책을 기준으로 scope를 검증해야 한다. 이 방식이 장기적으로 충분한지는 후속 검토가 필요하다.

## 6. 재고 조회/입출고/반품 루틴 기준

### 재고 조회

- `client_id`는 필수다.
- `warehouse_id`가 없으면 해당 `client_id`의 전체 창고 기준으로 조회한다.
- `warehouse_id`가 있으면 해당 `client_id` 소속 창고인지 검증한 뒤 해당 창고만 조회한다.
- “전체 창고”는 조회 조건의 부재 또는 UI 옵션으로만 표현한다.

### 입고

- 내부 운영자는 고객사를 선택하고, 고객사 사용자는 자기 고객사로 고정된다.
- 해당 고객사의 입고 가능 창고 중 하나를 선택한다.
- 기본 입고창고가 있으면 자동 적용할 수 있다.
- 수불은 `client_id + warehouse_id` 기준으로 기록한다.

### 출고

- 출고건의 `client_id`를 기준으로 한다.
- 해당 고객사의 기본 출고창고 또는 지정 창고에서 차감한다.
- 고객사 외 창고 차감은 금지한다.

### 반품 양품

- `GOOD` 또는 양품 판정 시 고객사의 기본 반품양품창고 또는 정책상 지정 창고로 입고한다.
- 필요 시 작업자가 고객사 소속 창고 중에서 변경할 수 있다.
- 변경 시 이력/사유 기록은 후속 검토 항목으로 둔다.

### 보류/리퍼/제조사반품

- 고객사 상세의 기본 보류, 리퍼, 제조사반품 창고를 우선 적용한다.
- 고객사 소속 창고만 선택 가능하다.
- 업무별 기본 창고가 없으면 해당 업무 화면에서 명확한 차단 또는 설정 유도 메시지를 보여준다.

## 7. 고객사 관리 화면 디자인 방향

고객사 관리 화면은 별도 창고설정 화면을 만들지 않고 고객사 상세 안에서 창고를 함께 관리하는 방향으로 설계한다.

추천 구조:

- 상단: 고객사 관리 제목, 신규 고객사 등록 버튼, 검색
- 본문 좌측 또는 중앙: 고객사 목록 `SmartDataGrid`
- 상세 영역 또는 상세 페이지:
  - 기본정보
  - 소속 창고
  - 기본 창고 설정
  - 담당자/메모
  - 사용 여부

고객사 상세의 소속 창고 영역:

- 창고 목록 `SmartDataGrid` 또는 작은 grid
- 창고 추가
- 창고명
- 창고코드
- 창고유형
- 사용 여부
- 메모
- 사용중지
- 기본 창고로 지정 가능

기본 창고 설정:

- 기본 입고창고
- 기본 출고창고
- 기본 반품양품창고
- 기본 보류창고
- 기본 리퍼창고
- 기본 제조사반품창고

고객사 관리는 입력 항목과 하위 목록이 많으므로 단순 모달보다 우측 상세 패널 또는 상세 페이지 패턴이 더 적합하다.

## 8. 기준정보 화면 공통 디자인 패턴

기준정보 화면은 관리자용 화면이다. 작업자 스캔 화면처럼 만들지 않는다.

공통 패턴:

- `SmartPage + SmartPageHeader + SmartToolbar + SmartDataGrid + SmartActionBar + SmartModalShell` 또는 상세 패널 구조를 우선한다.
- 목록은 `SmartDataGrid` 사용을 기본으로 한다.
- 등록/수정은 모달 또는 우측 상세 패널 중 화면 성격에 맞게 선택한다.
- 삭제보다 사용중지를 우선한다.
- 검색/필터는 상단 compact 영역으로 둔다.
- 주요 버튼은 오른쪽 상단 또는 하단 action bar에 배치한다.
- 1366x768에서 목록과 주요 버튼이 보여야 한다.
- 과한 카드 남발은 금지한다.
- 같은 기준정보 계열 화면은 같은 레이아웃과 같은 버튼 위치를 사용한다.

기준정보 화면은 “반복 조회 + 빠른 수정 + 사용중지/활성화 + 상세 확인”이 중심이므로, 안내 카드보다 grid와 상세 영역이 화면의 주인공이어야 한다.

## 9. 등록/수정 UI 패턴 선택 기준

### 모달이 적합한 경우

- 입력 항목이 적다.
- 빠른 등록/수정이 중요하다.
- 목록 흐름을 유지해야 한다.
- 예: 공통코드 단일 코드 추가, 단순 창고 추가, 상품 바코드 추가.

### 우측 상세 패널이 적합한 경우

- 입력 항목이 많다.
- 하위 목록이 있다.
- 고객사 상세처럼 창고 목록과 기본 설정을 함께 다뤄야 한다.
- 예: 고객사 상세, 상품 상세, 상품 바코드 목록 관리.

화면별 추천:

- 고객사 관리는 우측 상세 패널 또는 상세 페이지 패턴을 우선한다.
- 상품/상품바코드는 상품 상세 안에서 바코드 목록을 함께 관리하는 구조를 우선 검토한다.
- 공통코드는 코드그룹 목록 + 코드 목록의 2단 구조를 우선 검토한다.

## 10. 상품 관리 화면 디자인 방향

상품은 고객사별 기준정보다.

- 내부 사용자는 고객사를 선택한 뒤 해당 고객사 상품을 조회한다.
- 고객사 사용자는 자기 고객사 상품만 조회한다.
- 상품 목록은 `SmartDataGrid`를 사용한다.
- 상품 상세 안에서 상품 바코드를 함께 관리하는 구조를 우선 검토한다.
- 상품 바코드 단독 화면은 1차에서 만들지 않고 상품 상세의 하위 목록으로 처리하는 방향을 우선한다.
- `product_code`, `product_name`, `barcode`, `barcode_type`, `unit_qty`는 스캔, 입고, 출고, 반품에서 공통으로 쓰이므로 정확성을 우선한다.

상품 화면의 기본 흐름:

1. 고객사 선택 또는 scope 고정
2. 상품 목록 조회
3. 상품 등록/수정
4. 상품 상세에서 바코드 목록 관리
5. 사용중지/활성화

상품 목록에서는 `product_code`, `product_name`, 대표 `barcode`, `barcode_type`, `unit_qty`, 사용 여부, 수정일을 우선 표시한다. 업무 화면에서 실제 스캔 기준이 되는 값은 복사 가능하게 하되, 화면별 임시 table 기능으로 만들지 않고 `SmartDataGrid` 옵션을 사용한다.

## 11. 공통코드 관리 화면 디자인 방향

공통코드는 업무 분류값을 하드코딩하지 않기 위한 기준정보다.

- 코드그룹 목록 + 코드 목록 2단 구조를 우선 검토한다.
- 사용중지를 우선한다.
- 삭제는 후속 정책으로 제한한다.
- 표시순서 관리가 필요하다.
- 창고유형, 바코드유형, 반품판정, 반품사유, 보류사유, 택배사, 재고상태 등을 포함한다.

추천 화면 구조:

- 좌측: 코드그룹 목록 `SmartDataGrid`
- 우측: 선택 코드그룹의 코드 목록 `SmartDataGrid`
- 상단: 코드그룹 검색, 코드 검색, 사용 여부 필터
- 액션: 코드그룹 추가, 코드 추가, 수정, 사용중지, 활성화

공통코드는 많은 업무 화면의 select/lookup 기준이 되므로, 화면에서 직접 enum을 늘리지 않고 공통코드 관리 또는 backend 정책으로 통제한다.

## 12. API/DB 후속 검토 항목

현재 확인한 backend 구조:

- `Client` 모델은 `clients` 테이블이며 `client_code`, `client_name`, 연락처, 사용 모듈, `active_yn` 등을 가진다.
- `Warehouse` 모델은 `warehouses` 테이블이며 `warehouse_code`, `warehouse_name`, `warehouse_type`, 주소, `active_yn` 등을 가진다.
- 현재 `Warehouse` 모델에는 `client_id`가 없다.
- `ClientWarehouseSetting` 모델은 `client_warehouse_settings` 테이블이며 `client_id`, `warehouse_id`, `usage_type`, `is_default`, `active_yn`을 가진다.
- 현재 `client_warehouse_settings`에는 `unique(client_id, warehouse_id, usage_type)` 제약이 있다.
- read-only `GET /api/master/client-warehouses`는 `client_id` scope 기준으로 active client, active warehouse, active setting을 join해 조회한다.
- 관리 API는 `POST/PATCH/disable/enable/set-default /api/master/client-warehouses`로 고객사별 사용창고와 기본창고를 관리한다.
- `GET /api/master/warehouses`는 내부 운영자만 전체 창고 목록을 조회할 수 있는 구조다.
- frontend 기준정보 실제 route/screen은 아직 없고, `MainLayout`에는 기준정보 준비중 메뉴만 있다.

후속 검토 항목:

- 현재 `warehouses` 테이블이 고객사 종속 구조인지 재검토한다. 현재 모델 기준으로는 직접 종속 구조가 아니다.
- 현재 `client_warehouse_settings` API/테이블이 전역 창고 연결 구조인지 확인하고, 고객사 종속 창고 정책과 충돌하는지 판단한다.
- 기존 구조가 고객사 종속 창고 정책과 맞지 않으면 migration/리팩토링 후보로 기록한다.
- `warehouse_id` 입력 API에서 `warehouse.client_id` 검증이 필요한지 확인한다. 현재 모델에는 `warehouse.client_id`가 없으므로 연결 테이블 기준 검증 또는 모델 변경이 필요할 수 있다.
- 고객사 사용자 권한에서 자기 `client_id` 창고만 보이도록 API 범위 제한이 충분한지 확인한다.
- 재고 조회 API에서 `warehouse_id` optional 처리 기준을 설계한다.
- “전체 창고”를 DB row로 만들지 않는 기준을 유지한다.
- 기본 입고/출고/반품양품/보류/리퍼/제조사반품 창고를 현재 `usage_type` + `is_default`로 충분히 표현할 수 있는지 확인한다.
- 고객사 상세 화면에서 창고 추가를 처리하려면 `warehouses` 생성과 `client_warehouse_settings` 생성이 한 화면에서 이어지는 UX/API 계약이 필요하다.

## 13. 다음 구현 순서 제안

추천 순서는 아래와 같다.

1. 현재 backend 창고 모델/API가 고객사 종속 정책과 맞는지 점검한다.
2. 필요 시 고객사/창고 backend 구조 보강 설계를 진행한다.
3. 고객사 관리 화면 상세 디자인 문서를 작성한다.
4. 고객사 관리 화면을 구현한다.
5. 상품 관리 화면 상세 디자인 문서를 작성한다.
6. 상품 관리 화면을 구현한다.
7. 공통코드 관리 화면 상세 디자인 문서를 작성한다.
8. 공통코드 관리 화면을 구현한다.

단, backend 창고 구조가 고객사 종속 정책과 크게 어긋나면 화면 구현 전에 backend 구조부터 정리해야 한다. 화면에서 고객사 종속 창고처럼 보이게만 만들고 backend가 전역 창고 구조를 유지하면, 이후 재고/입출고/반품 scope 검증에서 비용이 커진다.

## 14. closeout 결론

기준정보 1차 화면은 고객사 관리, 상품 관리, 공통코드 관리로 시작한다.

창고는 고객사 관리 안에서 고객사 소속 창고로 등록/관리한다. 전역 창고마스터 단독 화면과 고객사별 창고설정 단독 화면은 1차에서 만들지 않는다.

현재 backend 모델 기준으로는 `warehouses`가 직접 고객사 종속 구조가 아니고, `client_warehouse_settings`가 고객사-창고 연결과 기본창고 역할을 담당한다. 따라서 다음 작업은 화면 구현보다 backend 창고 모델/API 정책 적합성 점검을 우선 추천한다.

그 다음 후보는 고객사 관리 화면 상세 디자인 문서 작성이다. backend 구조가 정책에 맞거나 보강 방향이 확정된 뒤 고객사 관리 화면 구현으로 들어가는 것이 안전하다.
