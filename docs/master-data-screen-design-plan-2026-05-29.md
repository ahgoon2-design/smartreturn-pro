# 기준정보 화면 디자인 계획

## 1. 문서 목적

이 문서는 SmartReturn Pro 기준정보 화면을 구현하기 전에 디자인, UX, 화면 구조, 공통 컴포넌트 사용 기준, 장기 확장 방향을 정리한다.

기준정보는 고객사/셀러, 창고/처리장소, 상품/바코드, 공통코드, 사용자/권한, 택배사/대리점, 정산/계약 기준의 출발점이다. 이 영역을 화면마다 제각각 만들면 이후 입고, 출고, 반품, 재고, 정산, 고객사 포털 화면까지 반복 재작업이 발생한다.

따라서 이번 문서는 아래 목적을 가진다.

- 고객사/셀러, 창고/처리장소, 상품/바코드, 공통코드, 사용자/권한 화면의 우선순위와 관계를 정리한다.
- 동현 직접 운영형, CJ택배 대리점 SaaS형, 서브터미널 반품처리 마이크로센터형, 타택배사 확장형을 고려한다.
- 기준정보 화면이 `SmartPage`, `SmartPageHeader`, `SmartDataGrid`, `SmartModalShell`, `SmartActionBar` 등 공통 UI 기준을 따르도록 한다.
- 1차 구현은 단순하게 시작하되, 장기 사업 방향 때문에 나중에 전체 화면 구조를 다시 뜯어고치지 않도록 상위 구조를 먼저 고정한다.

이번 문서는 설계 문서다. frontend 구현, backend API 수정, DB schema 변경, migration, seed 변경, package 변경은 포함하지 않는다.

## 2. 기준정보 화면 전체 범위

기준정보 후보는 아래와 같다.

| 구분 | 화면 후보 | 역할 |
| --- | --- | --- |
| 고객/계약 | 고객사/셀러 관리 | 내부 운영자 또는 대리점이 관리하는 판매자, 브랜드, 화주 기준정보 |
| 고객/계약 | 고객사 상세 | 기본정보, 창고/처리장소, 상품 연결, 사용자, 계약/정산 후보를 모으는 상세 진입점 |
| 창고/장소 | 고객사별 창고/처리장소 설정 | 해당 고객사가 사용할 창고와 반품 처리장소, 기본값을 관리 |
| 상품 | 상품 관리 | 고객사별 상품 기본정보 관리 |
| 상품 | 상품바코드 관리 | 상품별 바코드, 바코드 유형, 묶음 수량 기준 관리 |
| 운영코드 | 공통코드 관리 | 화면과 업무 로직에서 사용하는 분류값 관리 |
| 계정 | 사용자/권한 관리 | 내부, 대리점, 고객사 사용자와 접근 범위 관리 |
| 네트워크 | 택배사/대리점 관리 | CJ택배 대리점 SaaS형, 타택배사 확장을 위한 장기 기준정보 |
| 네트워크 | 처리장소 관리 | 서브터미널, 마이크로센터, 외부 처리장소 등 반품처리 거점 관리 |
| 반품정책 | 반품 판정 정책 관리 | 상품군, 고객사, 처리장소별 판정 기준과 후속 처리 기준 |
| 정산 | 정산/계약 기준정보 | 계약 유형, 과금 주체, 정산 항목, 단가, 부가서비스 기준 |

1차 구현 범위와 장기 후보는 분리한다.

| 단계 | 포함 화면 | 판단 |
| --- | --- | --- |
| 1차 | 고객사/셀러 관리, 고객사 상세, 고객사별 창고/처리장소 설정 | 모든 업무 scope와 재고/반품 처리의 기준이므로 최우선 |
| 2차 | 상품 관리, 상품바코드 관리 | 스캔, 입고, 출고, 반품 판정 정확도에 직접 영향 |
| 3차 | 공통코드 관리 | 하드코딩 제거와 운영코드 확장에 필요 |
| 4차 | 사용자/권한 관리 | 인증/권한 기반이 안정된 뒤 화면화 |
| 장기 | 택배사/대리점, 처리장소 마스터, 반품 판정 정책, 정산/계약 기준정보 | 사업 모델 확장과 운영 고도화 단계에서 분리 설계 |

## 3. 1차 우선순위 제안

### 1순위: 고객사/셀러 관리와 고객사 상세 안의 창고/처리장소 설정

고객사/셀러는 모든 업무 데이터의 `client_id` scope 기준이다. 고객사 선택과 고객사별 창고/처리장소 설정이 먼저 고정되어야 입고, 출고, 반품, 재고, 정산 화면이 흔들리지 않는다.

1차에서 고객사 상세 안에 창고/처리장소 설정을 포함하는 이유는 다음과 같다.

- 사용자가 실제로 알고 싶은 것은 “이 고객사는 어디에서 입고/출고/반품처리되는가”다.
- 창고설정을 별도 메뉴로 앞세우면 고객사 맥락이 끊어진다.
- `client_warehouse_settings` API 보강도 고객사 상세 화면 요구사항에 맞춰 진행할 수 있다.

### 2순위: 상품 관리와 상품바코드 관리

상품과 바코드는 스캔, 반품 판정, 입고/출고 검수의 정확도와 직결된다. 상품 화면은 고객사별 상품 기준정보와 바코드 목록을 함께 관리하는 구조가 좋다.

상품/바코드를 2순위로 두는 이유는 다음과 같다.

- import preview와 validation 결과를 실제 기준정보 관리로 이어가기 위한 다음 도착지다.
- 반품처리에서 상품군과 바코드가 판정 정책의 출발점이 된다.
- 상품코드/바코드 중복과 사용 여부 정책을 빨리 고정해야 운영 데이터 품질이 안정된다.

### 3순위: 공통코드 관리

공통코드는 하드코딩을 줄이는 장치다. 다만 초기에는 backend enum과 seed로 운영 가능한 값도 있으므로, 고객사/상품 화면보다 뒤에 둔다.

공통코드 화면은 창고 usage_type, 바코드유형, 반품판정, 보류사유, 상품군, 택배사, 계약 유형 등으로 확장된다.

### 4순위: 사용자/권한 관리

현재 role과 permission 기반이 이미 존재하므로, 화면은 후순위로 둔다. 사용자/권한 화면은 보안 영향이 커서 고객사/대리점/처리장소 scope 정책이 더 선명해진 뒤 설계한다.

### 장기 후보

택배사/대리점 관리, 처리장소 마스터, 반품 판정 정책, 정산/계약 기준정보는 장기 사업 구조와 직접 연결된다. 1차 화면에 과도하게 섞지 않고, 고객사/셀러 구조가 이 확장을 막지 않도록 필드와 화면 배치를 열어둔다.

## 4. 고객사/셀러 화면 설계 방향

고객사를 단순 `client` row로만 보지 않는다. 장기적으로 아래 유형을 고려한다.

- 동현 직접 계약 고객사
- CJ택배 대리점 소속 고객사
- 타택배사 대리점 소속 고객사
- 중대형 브랜드 고객사
- 소규모 셀러

1차 화면은 너무 복잡하게 만들지 않는다. 다만 장기 확장을 막지 않도록 고객사 유형, 운영 주체, 계약 유형 같은 개념을 표시 후보로 둔다.

고객사 목록 후보 컬럼:

- 고객사명
- 고객사 코드
- 계약 유형
- 운영 주체
- 기본 처리장소 또는 기본 창고
- 사용 여부
- 등록일
- 수정일
- 관리 액션

고객사 목록 화면 기준:

- `SmartPage`를 사용한다.
- `SmartPageHeader`에 화면 제목, 설명, 신규 등록 액션을 둔다.
- 목록은 `SmartDataGrid`를 사용한다.
- 검색/필터는 상단 `SmartToolbar` 또는 `SmartFilterPanel` 기준으로 둔다.
- 등록/수정은 입력량에 따라 `SmartModalShell` 또는 상세 화면을 선택한다.
- 삭제보다 사용중지/비활성을 우선한다.
- 고객사 코드는 `copyable` 후보로 둔다.

1차에서 추천하는 검색/필터:

- 고객사명/코드 keyword
- 사용 여부
- 계약 유형
- 운영 주체

API 응답에 계약 유형, 운영 주체, 기본 처리장소 표시명이 없다면 화면에서 임의 추정하지 않고 “API 보강 후보”로 둔다.

## 5. 고객사 상세 화면 설계 방향

고객사 상세는 탭 또는 섹션 구조로 설계한다.

후보 섹션:

- 기본정보
- 창고/처리장소 설정
- 상품/바코드 연결 현황
- 반품 판정 정책
- 사용자/계정
- 계약/정산 설정
- 처리 이력/변경 이력

1차 우선 섹션:

- 기본정보
- 창고/처리장소 설정
- 사용 여부/메모

후속 확장 후보:

- 상품/바코드 연결 현황
- 반품 판정 정책
- 사용자/계정
- 계약/정산 설정
- 처리 이력/변경 이력

고객사 상세는 단순 모달보다 상세 페이지 또는 우측 상세 패널이 적합하다. 창고/처리장소 설정처럼 하위 grid가 있는 화면은 작은 모달 안에 넣으면 1366x768에서 조작성이 떨어진다.

고객사 상세의 기본정보 영역 후보:

- 고객사명
- 고객사 코드
- 계약 유형
- 운영 주체
- 대표 연락처
- 사용 여부
- 메모

고객사 상세의 액션 후보:

- 저장
- 사용중지
- 활성화
- 변경 이력 보기
- 닫기 또는 목록으로 돌아가기

## 6. 창고/처리장소 설계 방향

기존 `docs/client-warehouse-settings-api-plan-2026-05-29.md` 기준을 따른다.

반드시 아래 개념을 구분한다.

| 개념 | 의미 | 예시 |
| --- | --- | --- |
| 창고 | 재고를 보관하고 수불이 발생하는 장소 | 입고창고, 출고창고, 반품양품창고, 보류창고 |
| 처리장소 | 반품을 검수, 사진촬영, 판정하는 작업 장소 | 동현 물류센터 반품검수존, 대리점 마이크로센터, 서브터미널 처리부스 |

현재 1차 구현은 `warehouses`와 `client_warehouse_settings`를 활용한다. 장기적으로는 `processing_site` 개념이 필요할 수 있다.

고객사 상세 안에서 창고/처리장소 설정을 관리하는 방향을 우선 추천한다. 별도 “창고설정” 메뉴를 앞세우지 않는다.

창고/처리장소 설정 후보 컬럼:

- 사용 유형 `usage_type`
- 창고명
- 창고 코드
- 기본 여부
- 사용 여부
- 처리 가능 업무
- 관리 액션

정책:

- 고객사별 `usage_type`당 active default는 1개다.
- inactive setting은 기본창고가 될 수 없다.
- 삭제보다 disable을 우선한다.
- 기본창고 disable은 차단하거나, 기본 해제 후 처리해야 한다.
- “전체 창고”는 DB row가 아니라 조회 옵션이다.
- 처리장소가 창고와 동일한 물리 위치일 수는 있지만, 개념은 분리해 둔다.

처리장소 장기 후보 필드:

- 처리장소명
- 처리장소 코드
- 소속 운영 주체
- 처리 가능 업무
- 사진촬영 가능 여부
- 라벨/프린터 연동 여부
- 사용 여부

1차 화면에서는 처리장소를 창고 설정의 설명/처리 가능 업무 정도로 흡수하고, 별도 처리장소 마스터는 장기 후보로 둔다.

## 7. 상품/바코드 화면 설계 방향

상품과 바코드는 반품판정과 연결될 수 있게 설계한다.

상품 목록 후보 컬럼:

- 상품코드
- 상품명
- 브랜드
- 상품군
- 대표 바코드
- 바코드 수
- 사용 여부
- 관리 액션

상품 상세 후보 섹션:

- 기본정보
- 바코드 목록
- 상품군/판정 정책 후보
- 메모/이력

상품바코드 후보 컬럼:

- 바코드
- 바코드 유형
- `unit_qty`
- 대표 여부
- 사용 여부
- 등록일
- 관리 액션

원칙:

- 상품코드와 바코드는 `copyable`로 둔다.
- 바코드는 중복 방지가 필요하다.
- 상품군은 장기적으로 판정 템플릿과 연결한다.
- 식품, 의류, 생활용품 등 상품군별 판정 확장을 고려한다.
- 상품바코드 단독 화면보다 상품 상세 안의 하위 grid를 우선한다.
- 내부 운영자는 고객사를 선택한 뒤 해당 고객사 상품을 본다.
- 고객사 사용자는 자기 고객사의 상품만 본다.

상품 화면의 API 보강 후보:

- 상품 목록용 대표 바코드
- 상품 목록용 바코드 수
- 상품 상세 + 바코드 목록 통합 조회
- 상품군 표시명
- 사용중지 포함 조회 옵션

## 8. 공통코드 화면 설계 방향

공통코드는 하드코딩을 줄이는 핵심 화면이다.

관리 후보:

- 반품 판정 상태
- 보류 사유
- 폐기 사유
- 상품군
- 택배사
- 계약 유형
- 처리장소 유형
- 창고 `usage_type`
- 정산 항목
- 사진 유형

원칙:

- 화면별 Select 하드코딩을 금지한다.
- 코드 그룹/코드 구조를 유지한다.
- 삭제보다 사용중지를 우선한다.
- 정렬순서 관리가 필요하다.
- 코드값 변경은 영향이 크므로 신중히 설계한다.
- 운영 중 표시명 변경과 시스템 코드 변경은 구분한다.

추천 구조:

- 좌측 또는 상단: 코드 그룹 목록
- 우측 또는 하단: 선택 코드 그룹의 코드 목록
- 목록은 모두 `SmartDataGrid` 기준
- 등록/수정은 `SmartModalShell` 기준
- 주요 액션은 코드 그룹 추가, 코드 추가, 수정, 사용중지, 활성화

공통코드 화면은 3순위지만, 기준정보 화면 전반의 select/lookup을 안정화하려면 너무 늦게 미루면 안 된다.

## 9. 사용자/권한 화면 설계 방향

사용자/권한 화면은 1차에서는 후순위로 둔다.

장기 사용자 유형:

- 동현 슈퍼관리자
- 동현 관리자
- 동현 작업자
- 대리점 소유자
- 대리점 관리자
- 대리점 작업자
- 셀러 관리자
- 셀러 사용자
- 읽기전용 사용자

원칙:

- 현재 backend role 구조와 충돌하지 않게 장기 후보로 관리한다.
- 고객사, 대리점, 처리장소 범위 제한이 필요하다.
- 사용자 화면은 인증/권한 안정화 후 진행한다.
- `SUPER_ADMIN`, `INTERNAL_ADMIN`, `INTERNAL_WORKER`, `CLIENT_ADMIN`, `CLIENT_USER`, `READ_ONLY` 현재 role은 P0 기준으로 유지한다.
- 대리점 role은 바로 추가하지 않고 사업 모델과 권한 경계를 별도 문서에서 확정한다.

사용자/권한 화면은 보안 사고 비용이 크므로 단순 CRUD 화면처럼 만들지 않는다. 권한 변경 이력, 비활성화, 비밀번호 초기화, must_change_password 처리 흐름을 함께 검토해야 한다.

## 10. 택배사/대리점 구조 설계 방향

택배사/대리점 구조는 지금 당장 화면 제작하지 않는다. 장기 확장 후보로 정리한다.

장기 개념:

- `carrier`
- `carrier_agency`
- `agency_seller`
- `processing_site`
- `contract_owner_type`
- `billing_target`

확장 방향:

- 동현 직접 운영형: 동현이 고객사와 직접 계약하고 자체 처리장소에서 처리한다.
- CJ택배 대리점 SaaS형: 대리점이 자기 소속 고객사와 처리장소를 관리한다.
- 서브터미널 반품처리 마이크로센터형: 처리장소가 여러 대리점 또는 고객사의 반품을 처리한다.
- 타택배사 확장형: CJ 외 택배사와 대리점 구조를 수용한다.

기준정보 화면 설계 시 고객사/셀러 구조가 이 확장을 막지 않아야 한다.

1차에서 하지 않을 것:

- 대리점 owner role 추가
- carrier/agency DB schema 확정
- processing_site 별도 화면 구현
- 정산 대상별 과금 구조 구현

1차에서 열어둘 것:

- 고객사/셀러 목록에 계약 유형과 운영 주체 표시 후보
- 고객사 상세에 처리장소 확장 후보
- 공통코드에 계약 유형, 택배사, 처리장소 유형 후보

## 11. 화면 디자인 공통 기준

`docs/skills/ui-design-system.md`와 `docs/skills/ui-grid.md` 기준을 따른다.

모든 기준정보 화면은 아래 공통 컴포넌트를 우선 사용한다.

- `SmartPage`
- `SmartPageHeader`
- `SmartToolbar` 또는 `SmartFilterPanel`
- `SmartDataGrid`
- `SmartModalShell`
- `SmartActionBar`
- `SmartStatusBadge`
- `SmartErrorNotice`

원칙:

- 화면마다 다른 table 사용을 금지한다.
- 모든 grid는 `SmartDataGrid`를 사용한다.
- 1366x768에서 주요 버튼과 그리드가 보여야 한다.
- 과한 카드 남발을 금지한다.
- 조회형 화면은 목록/검색이 먼저 보여야 한다.
- 등록/수정은 모달 또는 상세 패널 기준을 통일한다.
- 삭제보다 비활성/사용중지를 우선한다.
- 상태는 색상만으로 표현하지 않고 한글 문구와 badge를 함께 사용한다.

현재 frontend 공통 구조:

- `frontend/src/components/common`: `SmartActionBar`, `SmartErrorNotice`, `SmartPage`, `SmartPageHeader`, `SmartStatusBadge`, `SmartSummaryCard`
- `frontend/src/components/grid`: `SmartDataGrid`, `SmartDataGrid.types`, `SmartDataGrid.helpers`, `SmartGridStatusCell`, `SmartGridActionCell`, `SmartGridToolbar`
- `frontend/src/layouts/MainLayout.tsx`: 업무 화면 공통 shell
- `frontend/src/routes`: 보호 route와 route 정의

현재 없는 공통 컴포넌트 후보:

- `SmartToolbar`
- `SmartFilterPanel`
- `SmartModalShell`
- `SmartFormSection`
- `SmartLookupModal`
- `SmartCommonCodeSelect`

기준정보 화면 구현 전에 위 후보 중 1차에 꼭 필요한 것을 최소 구현하는 방향이 좋다.

## 12. 기준정보 화면 메뉴 구조 제안

추천 메뉴 구조:

```text
기준정보
  고객사/셀러
  상품/바코드
  공통코드
  사용자/권한
  택배사/대리점(장기 후보 또는 숨김)
```

고객사별 창고/처리장소 설정은 별도 메뉴로 빼기보다 고객사 상세 안에 둔다.

이유:

- 창고/처리장소 설정은 고객사 맥락이 있어야 이해하기 쉽다.
- 별도 메뉴로 분리하면 전역 창고마스터처럼 오해될 수 있다.
- 고객사 상세에서 기본 입고/출고/반품 처리 기준까지 한 번에 확인하는 편이 운영자 UX에 맞다.

메뉴 노출 기준:

- 내부 운영자: 기준정보 전체 메뉴 접근 후보
- 고객사 사용자: 자기 고객사 상품/창고 조회 후보만 후속 검토
- READ_ONLY: 조회 전용 후보
- 대리점 사용자: 장기 role 설계 후 노출 후보

## 13. API 보강 필요 후보

이번 문서에서 API 스펙을 확정하지 않는다. 화면 구현 전 검토해야 할 보강 후보만 정리한다.

고객사/셀러:

- 고객사 목록 화면용 response 필드
- 고객사 상세 API
- 고객사 상태 변경 API
- 계약 유형/운영 주체 표시 필드

고객사별 창고/처리장소:

- 고객사별 창고/처리장소 nested API
- 창고 후보 조회 API
- 비활성 포함 조회 옵션
- `client_warehouse_settings` response의 `usage_type_name`, `warehouse_type`, `warehouse_active_yn`, timestamps
- 처리장소 개념 도입 여부

상품/바코드:

- 상품 목록 화면용 대표 바코드
- 상품 목록 화면용 바코드 count
- 상품 상세 + 바코드 목록 API
- 상품군 표시명
- 상품/바코드 사용중지 포함 조회 옵션

공통코드:

- 코드그룹/코드 관리 화면용 pagination/filter
- 코드 정렬순서 변경 API
- 사용중지/활성화 API
- 코드값 변경 영향 검토

사용자/권한:

- role/permission 관리 화면 API
- 사용자 scope 표시 API
- 고객사/대리점/처리장소 범위 제한 API

주의:

- 화면에서 API 응답 필드를 임의 추정하지 않는다.
- 부족한 필드는 “API 보강 후보”로 남기고 후속 API 설계/구현에서 처리한다.

## 14. 구현 순서 제안

추천 순서:

1. 고객사/셀러 화면 API 부족분 확인
2. 고객사/셀러 목록 화면 skeleton
3. 고객사 상세 기본정보 skeleton
4. 고객사 상세 안의 창고/처리장소 설정 skeleton
5. 필요한 `client_warehouse_settings` API 보강
6. 상품/바코드 화면 설계 및 API 확인
7. 공통코드 화면 설계 및 API 확인
8. 사용자/권한은 후순위

단, 화면 구현 전에 필요한 API 보강 여부를 먼저 판단한다.

판단 기준:

- 고객사 목록에 필요한 필드가 현재 API에 있는가?
- 고객사 상세에서 창고/처리장소 설정을 조회할 수 있는가?
- 고객사별 창고 후보와 기본 창고 설정 API가 화면 흐름을 만족하는가?
- 상품 목록에서 대표 바코드와 바코드 수가 필요한가?
- 공통코드 select를 화면별 하드코딩 없이 구성할 수 있는가?

API 부족분이 화면 skeleton을 막지 않는다면, skeleton을 먼저 만들고 부족 필드를 후속 보강 후보로 둔다. 반대로 고객사 상세/창고 설정처럼 화면 핵심 흐름이 API에 없으면 API 보강을 먼저 진행한다.

## 15. 현재 개발 순서와의 관계

이번 문서는 기준정보 화면 구현 전 디자인 계획 문서다.

현재까지 완료된 단계:

- docs/skills 정리
- React/Vite/TypeScript 앱 스캐폴드
- AuthContext 실제 로그인 / Route Guard 연결
- SmartDataGrid 설계 문서 작성
- SmartDataGrid 최소 wrapper 구현
- Import Preview를 SmartDataGrid 계약으로 전환

문서화 후 다음 작업은 기준정보 화면/API 보강 순서 확정이다.

`client_warehouse_settings` API 보강 구현은 이 문서 기준에 맞춰 후속으로 진행한다. 파일 업로드 `EXCEL_FILE` skeleton은 기준정보 1차 방향을 잡은 뒤 진행한다.

이 순서를 추천하는 이유:

- 기준정보가 정리되어야 import validation 결과를 실제 상품/바코드 기준정보와 연결할 수 있다.
- 고객사/창고/처리장소 scope가 정리되어야 파일 업로드 이후 업무 데이터 반영 흐름이 안전해진다.
- `EXCEL_FILE` skeleton이 먼저 진행되면 import 화면은 늘어나지만 기준정보와 연결되는 도착점이 불안정할 수 있다.

## 16. closeout 결론

기준정보는 고객사/셀러부터 시작한다.

고객사 상세 안에 창고/처리장소 설정을 포함한다. 상품/바코드와 공통코드는 다음 단계로 둔다. 사용자/권한은 인증/권한 정책이 더 안정된 뒤 화면화한다.

택배사/대리점 구조는 장기 확장 후보로 고려하되, 1차 화면을 과하게 복잡하게 만들지 않는다. 다만 고객사/셀러 화면의 계약 유형, 운영 주체, 처리장소 후보는 장기 확장을 막지 않도록 열어둔다.

모든 기준정보 화면은 `SmartDataGrid`와 공통 UI 기준을 사용한다. 화면마다 임시 table/custom UI를 만들지 않는다.

다음 추천 작업은 이 문서 결과를 기준으로 고객사/셀러 화면 API 부족분을 확인하는 것이다. API 부족분이 화면 skeleton을 막지 않는다면 고객사/셀러 목록 화면 skeleton으로 진행하고, 핵심 흐름이 부족하다면 API 보강을 먼저 진행한다.
