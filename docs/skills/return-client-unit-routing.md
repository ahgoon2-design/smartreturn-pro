# 고객사 운영단위/팀 반품·창고·재고 라우팅 기준

## 문서 목적

- 고객사 내부 팀/운영단위 기준으로 반품 접수부터 재고반영까지 일관되게 처리하기 위한 규칙을 정리한다.
- 판정별 창고를 하드코딩하지 않고, 고객사/팀/판정 기준 라우팅 설정으로 관리한다.
- 팀별 재고와 창고별 재고가 맞도록 설계한다.

## 핵심 원칙

- 반품 row는 `client_id`만으로 부족하다.
- 고객사 내부 팀/운영단위인 `client_unit_id` 또는 유사 개념을 접수 시점부터 일마감/재고반영까지 끌고 다닌다.
- 수동등록 반품은 등록 시 고객사와 함께 팀/운영단위를 선택할 수 있어야 한다.
- 네이버/쿠팡/API 자동수집 반품은 팀을 모르면 `TEAM_ASSIGN_PENDING` 상태로 들어올 수 있다.
- 담당자는 자기 팀 반품임을 확인하고 팀을 배정해야 한다.
- 팀이 배정되면 해당 팀 기준 기본 창고와 판정별 창고 추천이 가능해야 한다.
- 일마감/재고반영 시 최종 창고가 없으면 재고반영을 차단한다.
- 창고 자동 배정은 강제값이 아니라 기본 추천값이다.
- 작업자는 필요 시 창고를 변경할 수 있어야 한다.
- 변경 이력은 후속 구현에서 남길 수 있어야 한다.

## 고객사 운영단위 개념

문서에서는 `client_unit`, `client_operating_unit`, `client_team` 후보 개념을 묶어 “고객사 운영단위/팀”으로 표현한다.

예시:
- 고객사: 이에스피마케팅
- 온라인팀 -> 온라인창고
- 공구팀 -> 공구창고

후보 필드:
- `client_unit_id`
- `client_id`
- `unit_code`
- `unit_name`
- `unit_type`
- `default_warehouse_id`
- `return_warehouse_id`
- `active_yn`
- `sort_order`
- `memo`

이번 문서는 구현하지 않고 후보 기준만 정리한다.

## 반품 접수 시 팀 처리 규칙

수동등록:
- 고객사를 선택한다.
- 팀/운영단위를 선택한다.
- 반품 row에 `client_unit_id`를 저장한다.

자동수집:
- 고객사를 먼저 매칭한다.
- 팀이 확정되지 않으면 `TEAM_ASSIGN_PENDING` 상태로 둔다.
- 담당자가 팀을 확인한 뒤 배정한다.
- 배정 후 반품처리, 판정, 일마감, 재고반영까지 `client_unit_id`를 유지한다.

필수 원칙:
- 팀이 필요한 고객사는 팀 미배정 상태로 반품처리/재고반영이 진행되면 안 된다.
- 팀이 필요 없는 고객사는 `client_unit_id` 없이 고객사 기본 라우팅을 사용할 수 있다.

## 판정별 창고 라우팅 규칙

하드코딩 금지:
- `GOOD=온라인창고` 같은 코드를 직접 박지 않는다.
- `REFURB_A=리퍼A창고` 같은 코드를 직접 박지 않는다.

판정별 창고 라우팅은 아래 후보 구조로 관리한다.
- `client_id`
- `client_unit_id` nullable
- `judgement_status`
- `default_warehouse_id`
- `inventory_reflect_type`
- `label_print_default`
- `followup_type`
- `allow_worker_override`
- `active_yn`

라우팅 우선순위:
1. 고객사 + 팀 + 판정 라우팅
2. 고객사 + 판정 라우팅
3. 고객사 기본 창고 설정
4. 없으면 재고반영 차단

## 판정 예시

아래는 운영 기본값 예시일 뿐이며, 코드에 하드코딩하지 않는다. 업체마다 다를 수 있으므로 고객사/팀별 설정으로 관리한다.

- `GOOD` -> 온라인창고
- `MANUFACTURER_RETURN` -> 온라인반출창고
- `REFURB_A` -> 리퍼A창고
- `REFURB_B` -> 리퍼B창고
- `REFURB_C` -> 리퍼C창고
- `SAMPLE` -> 샘플창고
- `DISPOSAL` -> 폐기창고
- `HOLD` -> 보류상태 유지 또는 보류창고 후보

## 재고반영 규칙

- 판정 저장 즉시 재고반영하지 않는다.
- 판정 완료 후 수량체크/일마감 확정 시 재고반영한다.
- `GOOD`뿐 아니라 `REFURB_A`, `REFURB_B`, `REFURB_C`, `SAMPLE`, `MANUFACTURER_RETURN`, `DISPOSAL`도 고객사 정책에 따라 지정 창고로 재고반영할 수 있어야 한다.
- `HOLD`는 확정 판정이 아니므로 기본적으로 재고반영하지 않는다.
- 일마감/재고반영 시 최종 창고가 없으면 failed 처리한다.
- 같은 row의 중복 재고반영을 차단한다.

## 현장 반품처리 방식

- 반품처리 화면은 스캔 처리와 그리드 선택 처리를 모두 지원한다.
- 운송장 스캔으로 세부 row가 조회되면 상품 바코드/상품코드 스캔을 우선 사용한다.
- 스캔이 어렵거나 소량 예외 건이면 그리드 row를 선택하고 실물 확인 후 판정할 수 있다.
- 그리드 선택 처리도 `SCAN`, `GRID_SELECT`, `MANUAL_QUANTITY`, `BULK_CONFIRM` 같은 처리방식 이력으로 구분해 남길 수 있어야 한다.
- 처리수량은 기준수량을 초과할 수 없고, 이미 처리완료된 row는 중복 처리할 수 없다.
- 운송장만 있고 세부항목이 없으면 “세부항목 없는 반품”으로 보고, 상품마스터 기준 상품코드/바코드와 수량을 수동 등록한 뒤 처리대상으로 전환한다.
- 상품마스터에 없는 상품은 정상 처리하지 말고 확인필요 또는 보류로 분리한다.
- `return_tracking_no`는 현장 스캔 기준이고 `original_tracking_no`는 원주문 보조 조회 후보이다.
- 업체 반품 세부정보와 CJ 반품 운송장 정보는 반품처리 참고자료이며, 실제 상품/수량/판정은 현장 반품처리 원장에서 확정한다.

### 세부항목 없는 반품 현장 처리

- 세부항목 없는 반품은 반품처리 화면에서 바로 상품 스캔 또는 상품 검색/선택으로 처리 row를 생성한다.
- 반품 자료 등록 화면으로 이동하는 것은 보조 경로이며, 현장 처리를 막는 기본 흐름이 되면 안 된다.
- 상품마스터에 없는 상품은 정상 처리완료하지 않는다. 확인필요 또는 보류로 분리한 뒤 상품 연결 후 처리한다.
- 판정 저장 전 고객사별 판정/창고 라우팅 또는 기본 창고 기준으로 `warehouse_id`가 확정되어야 한다.
- `warehouse_id` 확정 전에는 처리완료할 수 없다.
- 반품 처리완료는 재고반영이 아니며, 현재고는 일마감 또는 반출/폐기 확정 후 반영한다.
- 스캔 처리와 그리드 선택 처리는 같은 backend 검증과 이력 기록을 사용한다.

## 판정 버튼과 창고 확정

- 반품처리 화면의 판정 버튼은 고객사별 판정/창고 라우팅 설정에 등록된 항목을 우선 사용한다.
- 공통 판정 목록은 테스트 fallback일 뿐이며, 운영 기준으로 하드코딩하지 않는다.
- 판정 저장 시 고객사/팀/판정 기준 추천 창고를 적용하고, 최종 `warehouse_id`가 없으면 일마감 재고반영을 차단한다.
- 양품과 제조사반출처럼 창고 분기가 필요한 판정은 작업자가 추천 창고를 확인하거나 선택할 수 있어야 한다.
- 리퍼, 샘플, 폐기 등은 고객사 설정에 따라 기본 창고로 자동 배정할 수 있다.
- 일마감 확정 후에는 `client_id`, `client_unit_id`, `warehouse_id`, `product_id`, `judgement_status` 기준으로 재고를 반영한다.

## 관련 운영 기준

- 반품 판정, 세부항목 없는 반품, 스캔/그리드 처리, 부품적출의 상세 기준은 `return-operational-judgment-policy.md`를 따른다.
- 세트상품 반품, 구성품 체크, 부품적출 가능 여부는 `set-product-component-bom.md`를 함께 따른다.
- AI 판정 추천과 체크리스트는 `return-judgment-ai-assistant.md`를 따르며, 최종 판정과 창고 확정은 작업자가 수행한다.

## 향후 구현 순서 제안

1. 고객사 운영단위/팀 기준정보 skeleton
2. 반품접수 row에 `client_unit_id` 연결
3. 팀배정대기/팀배정 화면 skeleton
4. 판정별 창고 라우팅 설정 skeleton
5. 일마감/재고반영을 고객사 + 팀 + 판정별 창고 기준으로 보강
6. 재고현황에서 고객사/팀/창고별 조회 보강
