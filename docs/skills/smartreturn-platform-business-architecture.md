# SmartReturn 플랫폼 사업/제품 아키텍처 스킬

## 목적

SmartReturn Pro는 반품 전용 프로그램이 아니다.
SmartReturn Pro의 최종 목표는 CJ대한통운 대리점과 함께 운영 가능한 OMS + WMS + Returns 통합 SaaS 플랫폼이다.
초기 MVP는 반품 자동화 중심으로 시작하지만, DB, 권한, 메뉴, 화면, 채널연동, 정산, 인프라는 향후 대리점, 셀러, 현장 작업자, 본사 관리자가 함께 사용하는 플랫폼으로 확장 가능해야 한다.

핵심 기준은 다음 문장으로 고정한다.

> 반품은 시작점이고, 목표는 CJ대한통운 대리점 기반 통합 물류 플랫폼이다.

이 문서는 신규 기능, DB 테이블, 메뉴, 권한, 화면, 채널 연동, 정산, 대리점 포털, 고객사 포털을 설계할 때 최상위 제품 방향을 확인하기 위한 기준 문서다.

## 왜 반품부터 시작하는가

- 반품은 셀러가 가장 불편해하는 업무 중 하나다.
- 네이버, 쿠팡 등 채널 반품 자료, 수거송장, 입고검수, 사진, 판정, 재고반영이 엑셀, 구글시트, 수기 업무로 흩어져 있다.
- CJ대한통운 대리점은 기존 택배 영업 외에 반품 처리, 검수, 재고, 셀러 포털 서비스를 묶어 추가 수익을 만들 수 있다.
- 반품 자동화는 플랫폼 진입 상품이며, 이후 OMS, WMS, 정산, 대리점 포털로 확장한다.
- 따라서 현재 반품 기능을 작게 만들더라도 구조는 플랫폼 확장을 전제로 해야 한다.

현재 반품 MVP는 플랫폼의 시작점이다. 반품 화면 몇 개를 빠르게 만드는 것이 아니라, 향후 주문, 재고, 출고, 정산, 포털, 채널 API까지 연결될 수 있는 공용 데이터와 권한 구조를 먼저 지켜야 한다.

## 플랫폼 사업 구조

### SmartReturn 본사/운영사

- 플랫폼 개발과 운영을 담당한다.
- 대리점 관리, 요금제, 정산 정책을 관리한다.
- 네이버클라우드 인프라를 운영한다.
- 채널 API, 택배 API, 알림 API 연동 기준을 관리한다.
- 대형 고객, 대리점, 셀러 직접가입 모델을 함께 고려한다.

### CJ대한통운 대리점

- 자기 계약 셀러와 고객사를 관리한다.
- 반품 물량을 유치한다.
- 반품 입고, 검수, 라벨, 재고 서비스를 제공한다.
- 셀러에게 반품서비스료 또는 부가서비스료를 청구할 수 있다.
- SmartReturn 본사에 SaaS 사용료 또는 가맹/플랫폼 수수료를 납부할 수 있다.

주의: CJ대한통운 공식 제휴, 공식 계약, 브랜드 사용, 본사 연동은 실제 협의 전에는 확정 표현을 쓰지 않는다. 문서와 화면에서는 “CJ대한통운 대리점과 함께 운영 가능한 플랫폼”처럼 신중한 표현을 사용한다.

### 셀러/고객사

- 네이버, 쿠팡, 카페24 등 채널 반품 자동수집을 사용한다.
- 반품 입고 상태를 확인한다.
- 검수 결과와 사진을 확인한다.
- 재고를 확인한다.
- 정산과 청구 내역을 확인한다.
- 필요 시 출고, 입고, 주문 관리 기능까지 사용한다.

### 현장 작업자

- 입고 스캔을 수행한다.
- 상품 스캔과 수량 확인을 수행한다.
- 판정과 보류 처리를 수행한다.
- 사진과 증빙을 등록한다.
- 라벨을 출력한다.
- 일마감과 수량체크를 수행한다.
- 외부반출과 출고검수를 수행한다.

## 사용자 유형

- `SUPER_ADMIN` / 플랫폼 본사 관리자: 전체 대리점, 고객사, 채널, 정산, 시스템을 관리한다.
- `AGENCY_ADMIN` / CJ대한통운 대리점 관리자: 자기 대리점 소속 고객사, 셀러, 작업 현황, 정산을 관리한다.
- `CLIENT_ADMIN` / 고객사 관리자: 자기 회사의 반품, 재고, 정산, 상품, 채널 상태를 확인하고 관리한다.
- `CLIENT_USER` / 고객사 일반 사용자: 제한된 조회, 요청, 확인 기능을 사용한다.
- `WAREHOUSE_MANAGER` / 창고 관리자: 입고, 출고, 재고, 일마감, 작업자 운영을 관리한다.
- `WORKER` / 현장 작업자: 스캔, 검수, 판정, 라벨, 마감 등 작업 화면을 사용한다.
- `SUPPORT` / 고객지원 또는 운영지원: 권한 범위 안에서 조회와 지원 업무를 수행한다.

내부 운영자 화면, 대리점 포털, 고객사 포털, 작업자 화면은 같은 DB와 공통 로직을 사용하되 사용자 유형과 권한에 따라 메뉴와 화면을 다르게 보여준다. 고객사 포털을 별도 앱으로 만들더라도 DB는 같은 운영 DB를 공유하는 구조를 기본으로 한다.

## 데이터 계층 구조

SmartReturn Pro의 기본 데이터 계층은 다음 방향을 따른다.

```text
platform_owner
-> agency_id
-> client_id
-> client_unit_id
```

정책:

- 초기 구현부터 `agency_id` → `client_id` → `client_unit_id` 3단계 계층을 기본으로 둔다.
- `agency_id`는 나중에 붙이는 보조 필드가 아니라 대리점 SaaS 권한, 통계, 정산, 운영 이력의 상위 scope다.
- 신규 운영 테이블을 만들 때는 `agency_id` 직접 저장 여부를 먼저 검토하고, 핵심 운영/대량 이력 테이블은 원칙적으로 `agency_id`를 직접 가진다.
- 모든 고객사 운영 데이터는 `client_id` 포함을 우선 검토한다.
- 팀, 브랜드, 창고, 운영단위 구분이 필요한 데이터는 `client_unit_id`를 포함한다.
- 대리점 단위 운영, 정산, 권한이 필요한 데이터는 `agency_id`를 포함해 저장한다.

예시:

- `agency_id`: CJ대한통운 대리점
- `client_id`: 셀러/고객사
- `client_unit_id`: 고객사 내부 팀, 브랜드, 창고, 운영단위

주의:

- 반품 row를 `client_id`만으로 끝내지 않는다.
- 반품 접수부터 재고반영, 정산까지 `client_unit_id`를 가능한 유지한다.
- 대리점 확장을 막는 단일 회사 내부용 구조로 고정하지 않는다.
- `return_intake_rows`, `channel_raw_events`, `channel_return_candidates`, `product_channel_mappings`, `inventory_events`, `current_inventory`, `import_jobs`, `import_job_rows` 같은 핵심 운영/이력 테이블은 join만으로 대리점 범위를 유추하지 말고 `agency_id`를 직접 보존한다.

초기 MVP는 “반품 자동화 중심 플랫폼 진입 상품”으로 정의한다.

초기 MVP 필수:

- 고객사/팀/`client_unit` 관리
- 상품/바코드 마스터

- Smart Import Mapper
- 네이버/채널 자동수집 기반
- 반품예정자료 생성
- 운송장 스캔
- 상품 스캔
- 판정
- 사진/증빙 선택 등록
- 라벨/반품관리번호
- 일마감/수량체크
- 재고반영
- 외부반출
- 반품 이력
- 고객사/대리점 확장 가능한 권한 구조
- 네이버클라우드 SaaS 운영 기준

초기 MVP에서 무리하지 않아도 되는 것:

- 전체 OMS 완성
- 전체 WMS 완성
- 고급 정산 자동화

- 모든 채널 API 실연동
- AI 자동판정
- 완전 자동 채널 승인/보류

## 메뉴/화면 방향

SmartReturn Pro의 메뉴와 화면은 반품 프로그램처럼 보이면 안 된다. 초기에는 반품 메뉴가 많더라도 전체 인상은 OMS + WMS + Returns 통합 플랫폼이어야 한다.

상위 메뉴 예시:

- 대시보드
- 주문/채널
- 입고
- 출고
- 재고
- 반품
- 정산
- 고객사/대리점
- 기준정보
- 채널연동
- 시스템/설정

정책:

- 초기 미구현 메뉴를 무리하게 실제 기능처럼 열어두지는 않는다.
- 단, 상위 메뉴 구조는 대시보드, 주문/채널, 입고, 출고, 재고, 반품, 정산, 고객사/대리점, 기준정보, 시스템 기준으로 잡아 반품 전용 프로그램처럼 보이지 않게 한다.
- 미구현 기능은 준비중/disabled로 둘 수 있지만, 기존 구현 화면은 플랫폼형 상위 메뉴 아래에 자연스럽게 배치한다.
- 반품 화면도 나중에 주문, 재고, 정산과 연결될 수 있게 설계한다.
- 고객사 포털과 대리점 포털은 같은 DB와 공통 로직을 기반으로 권한별 화면만 다르게 한다.

## DB/권한/인프라 기준 연결

플랫폼 방향이 필요한 작업에서는 이 문서와 아래 스킬을 함께 읽는다.

- `naver-cloud-saas-architecture.md`
  - 네이버클라우드 SaaS 운영
  - 단일 DB 멀티테넌트
  - Cloud DB for PostgreSQL
  - Object Storage
  - API/Worker/Scheduler 분리
- `return-client-unit-routing.md`
  - `client_unit` 기반 반품 접수, 처리, 재고반영 유지
- `return-operational-judgment-policy.md`
  - 고객사별 판정, 판정별 창고, 세부항목 없는 반품, 스캔/그리드 처리, 부품적출 기준
- `set-product-component-bom.md`
  - 세트상품/구성품/BOM을 출고, 반품, 부품적출에 연결하는 기준
- `return-judgment-ai-assistant.md`
  - AI를 최종 판정자가 아닌 고객사별 판정지원 도우미로 설계하는 기준
- `channel-return-auto-collection.md`
  - 네이버, 쿠팡, 카페24, 이지어드민, 택배사 API 수집자료를 공용 반품접수 흐름으로 연결
- `smartreturn-screen-design-system.md`
  - 플랫폼 화면은 현대적인 물류 SaaS 디자인을 따른다.

새 기능은 위 스킬들과 충돌하면 안 된다. 충돌할 때는 `AGENTS.md`의 보안, 문서 언어, 중단 조건을 최우선으로 하고, 그 다음 이 문서의 플랫폼 방향을 따른다.

## 정산/요금제 방향

정산은 플랫폼 사업의 핵심이므로 별도 모듈로 확장 가능해야 한다.

요금 경로:

- 대리점이 SmartReturn 본사에 납부하는 SaaS 사용료
- 셀러가 대리점에 납부하는 반품서비스료
- 대리점 없이 셀러가 직접 가입하는 직접가입 요금제
- 대형 고객 전용 계약 요금
- 건당 과금, 월정액, 물량 구간별 과금, 부가서비스 과금 가능성

정책:

- 초기에는 정산/청구를 완성하지 않아도 된다.
- 하지만 데이터 구조는 나중에 `usage_metering`, `billing`, `settlement`로 확장 가능해야 한다.
- 반품, 입고, 출고, 재고 이벤트는 나중에 사용량 집계의 근거가 될 수 있으므로 이력 보존이 중요하다.
- 정산을 위해 판정, 마감, 외부반출, 재고반영 이력은 명확해야 한다.

## CJ대한통운 대리점 사업 전략

SmartReturn Pro의 강한 확산 채널은 개별 셀러 영업뿐 아니라 CJ대한통운 본사, 대리점, 대리점 연합회와의 협력 가능성이다.

영업 메시지:

- “택배만 팔지 말고 반품서비스까지 묶어 추가 수익을 만드십시오.”
- “셀러가 힘들어하는 반품 수집, 입고, 검수, 사진, 재고, 정산을 대리점 서비스로 제공할 수 있습니다.”
- “대리점은 기존 택배 고객에게 반품 운영 서비스를 추가로 제안할 수 있습니다.”

확산 전략:

- 파일럿 대리점 1~2곳 선정
- 실제 셀러 반품 처리 성공사례 확보
- 처리 시간, 오류 감소, 사진 제공, 재고반영 사례 수집
- 사례집, PPT, 블로그로 전환
- 대리점 연합회 또는 본사 제안 자료로 활용

주의:

- CJ대한통운 공식 계약, 공식 연동, 브랜드 사용은 실제 협의 전 단정하지 않는다.
- 공식 제휴 여부는 실제 계약 전 확정 표현을 피한다.
- 제품 문구는 “CJ대한통운 대리점과 함께 운영 가능한 플랫폼”을 기준으로 한다.

## 개발 금지 방향

다음 방향은 금지한다.

- SmartReturn Pro를 반품 화면 몇 개짜리 단일 프로그램처럼 설계하는 것
- 고객사, 대리점, 셀러, 작업자 권한 확장이 불가능한 구조
- `client_id` 없이 운영 데이터를 저장하는 것
- `client_unit_id`가 필요한 업무에서 팀/운영단위를 잃어버리는 것
- 향후 `agency_id` 추가가 불가능한 구조
- 채널 수집자료를 화면별 개별 저장 로직으로 처리하는 것
- 반품 판정 즉시 재고를 반영하는 것
- 고객사별 DB 분리를 초기 기본값으로 잡는 것
- 사진/첨부파일을 DB blob으로 저장하는 것
- 대량 이력 테이블에 인덱스/보관정책 없이 계속 쌓는 것
- 내부 운영자 화면과 고객사 포털을 완전히 다른 DB/로직으로 분리하는 것
- 대리점 SaaS 확장을 고려하지 않은 메뉴/권한/정산 설계
