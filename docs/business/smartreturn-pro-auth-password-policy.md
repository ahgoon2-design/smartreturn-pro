# SmartReturn Pro 인증/비밀번호 정책

이 문서는 SmartReturn Pro 신규 제작 기준이다. 기존 SmartReturn의 구현기록, 권한 처리, 비밀번호 처리 방식을 그대로 따르지 않는다.

## role 기준 권한

- 내부 운영자: `SUPER_ADMIN`, `INTERNAL_ADMIN`, `INTERNAL_WORKER`
- 고객사 사용자: `CLIENT_ADMIN`, `CLIENT_USER`, `READ_ONLY`

## 사용자 성격 판단 기준

- `client_id` 유무로 사용자 성격을 판단하지 않는다.
- 내부 운영자는 고객사를 선택할 수 있다.
- 고객사 사용자는 자기 `client_id`로 고정된다.
- 내부 운영자에게 `client_id`가 있어도 고객사 사용자로 판단하지 않는다.

## 업무 데이터 접근 원칙

- 고객사 사용자는 자기 `client_id` 데이터만 접근한다.
- 내부 운영자는 권한 범위 안에서 고객사를 선택해 접근한다.
- 창고 업무는 `warehouse_id` scope도 함께 지킨다.
- 읽기 전용 사용자는 변경 API를 호출할 수 없다.

## 첫 로그인 비밀번호 정책

- 첫 로그인 사용자는 `must_change_password` 상태를 가질 수 있다.
- `must_change_password`가 true이면 비밀번호 변경 전 일반 업무 API를 차단한다.
- 비밀번호 변경 API와 로그아웃 같은 최소 API만 허용한다.
- 비밀번호 변경 완료 후 일반 업무 접근을 허용한다.

## 비밀번호 운영 정책

- 운영사 관리자는 비밀번호를 조회할 수 없다.
- 운영사 관리자는 초기화 또는 재발급만 할 수 있다.
- 평문 비밀번호를 응답하지 않는다.
- 임시 비밀번호 전달 방식은 별도 보안 기준을 따른다.
- 비밀번호 변경, 초기화, 실패 횟수 같은 보안 이벤트는 추적 가능해야 한다.

## Codex 구현 전 체크

- 내부 운영자와 고객사 사용자를 `role` 기준으로 구분했는가?
- `client_id` 유무로 사용자 성격을 판단하지 않았는가?
- 내부 운영자는 고객사를 선택할 수 있는가?
- 고객사 사용자는 자기 `client_id`로 고정되는가?
- `must_change_password` 상태에서 일반 업무 API가 차단되는가?
- 운영사 관리자가 비밀번호를 조회할 수 없게 했는가?
- 평문 비밀번호를 응답하지 않는가?
