# SmartReturn Pro 반품 MVP 상세 업무흐름

이 문서는 SmartReturn Pro 신규 제작 기준이며, 기존 SmartReturn 구현기록을 그대로 따르지 않는다.

이 문서는 화면 구현 지시가 아니라 반품 MVP의 업무 책임과 흐름을 고정하는 기준 문서다. 이후 화면 설계, DB 상세 설계, API 상세 설계는 이 문서를 기준으로 진행한다.

## 반품 MVP 기본 정의

- 반품은 SmartReturn Pro의 1차 핵심 업무 MVP다.
- 반품 MVP는 전체 반품 고도화가 아니라, 실제 현장에서 아래 흐름이 끊기지 않는 것을 목표로 한다.

```text
반품자료 준비
→ 반품처리 작업
→ 반품 마감
→ 반품 반출
→ 반품 통합추적
```

각 단계의 의미는 다음과 같다.

- 반품자료 준비: 외부 입력 자료를 내부 반품 작업 대상 후보로 만드는 단계.
- 반품처리 작업: 실제 도착한 반품을 스캔하고 상품/수량/판정을 확정하는 단계.
- 반품 마감: 판정 완료 결과를 기간/고객사/상태 기준으로 실물 대조하고 마감하는 단계.
- 반품 반출: 리퍼/제조사반품/샘플/보류 등 외부로 나갈 반품 개체를 스캔 검수하고 반출확정하는 단계.
- 반품 통합추적: 운송장, 반품관리번호, 작업번호 기준으로 이력을 조회하는 읽기 전용 화면.

## 반품 입력자료의 성격 분리

반품 MVP에서는 업체 반품접수 자료, 택배/CJ 반품예정 자료, 실제 반품처리 원장을 반드시 분리한다. 세 자료는 서로 연결될 수 있지만 같은 원장이 아니다.

## 업체 반품접수 자료

### 예시

- 업체 구글시트
- 업체 포털 입력
- 업체 엑셀 접수자료
- 향후 API 접수자료

### 정의

- 업체가 반품 요청, CS, 상품후보, 사유, 처리요청을 입력한 자료다.
- SmartReturn 내부 반품처리 원장이 아니다.
- 실제 도착 여부를 보장하지 않는다.
- 상품정보는 후보/참고값이다.
- 판정 결과를 회신할 수 있는 외부 채널일 수 있다.

### 금지

- 반품처리 작업 화면에서 구글시트 동기화를 실행하지 않는다.
- 현장 스캔 중 Google Sheets API를 직접 호출하지 않는다.
- 업체 접수자료가 없다는 이유만으로 실제 도착 반품 처리를 무조건 차단하지 않는다.

## 택배/CJ 반품예정 자료

### 예시

- CJ 반품예정 엑셀
- 타택배 반품예정 엑셀
- 운송장 중심 반품 도착 후보 자료

### 정의

- 운송장/입고번호 중심으로 실제 들어올 가능성이 있는 자료다.
- 상품정보는 부정확하거나 없을 수 있다.
- 상품/수량/판정 확정자료가 아니다.
- 고객사 매핑과 운송장 정규화가 중요하다.

### 금지

- 택배 예정자료의 상품명/수량만 믿고 재고를 반영하지 않는다.
- `batch_id`를 반품처리 중심키로 사용하지 않는다.

## 실제 반품처리 원장

### 정의

- 창고에서 실제로 스캔/확인/판정한 결과다.
- 최종 상품, 수량, 판정, 창고, 라벨, 재고 이벤트의 기준이다.
- 반품처리 작업에서 생성/확정된다.

### 기준

- 운송장번호가 있으면 운송장번호 기준으로 시작한다.
- 운송장번호가 없으면 내부 `work_batch_id`, `external_ref_no`, 반품입고번호 같은 내부 작업 식별자로 시작할 수 있다.
- 고객사와 상품이 확인되지 않은 정체불명 반품은 정상 반품자료로 등록하지 않는다.

## 반품자료 준비 상세 흐름

### CJ/택배 반품예정 등록

흐름은 다음과 같다.

```text
엑셀 선택
→ import job 생성
→ 원본 row 저장
→ 운송장 정규화
→ 고객사 매핑
→ 검증 결과 확인
→ 저장 확정
→ 반품예정 업무 테이블 반영
→ 저장자료 조회
```

포함 기능은 다음과 같다.

- 엑셀 업로드
- 엑셀 붙여넣기 후보
- 원본 미리보기
- 고객사 미매칭 표시
- 중복 운송장 표시
- 저장 확정
- 저장자료 조회
- 업로드 이력

넣지 말 것은 다음과 같다.

- 구글시트 동기화
- 반품 판정
- 라벨 출력
- 재고 반영
- 반품 마감
- 반품 반출

### 업체 반품접수 자료 관리

반품 MVP 1차에서는 업체 구글시트 실연동을 제외하고 문서상 구조만 둔다. 별도 “업체 반품접수 관리” 후보로 분리하고, 내부 반품입고예정 화면에는 넣지 않는다.

정책은 다음과 같다.

- 구글시트는 업체 반품접수/회신 채널이다.
- 내부 반품입고예정 화면과 섞지 않는다.
- 동기화된 업체자료는 반품처리 작업에서 참고정보로만 보여줄 수 있다.
- 구글시트 회신은 판정 완료 후 큐 방식으로 처리한다.

### 매칭 정책

- 반품접수자료와 반품예정자료는 매칭될 수도 있고 안 될 수도 있다.
- 매칭은 필수 관문이 아니다.
- 매칭이 없어도 고객사/상품이 확인된 실제 도착 반품은 처리 가능하다.
- 복수 후보가 있으면 작업자가 선택하거나 관리자 확인으로 보낸다.
- 자동매칭은 확정이 아니라 후보일 수 있다.

매칭 상태 예시는 다음과 같다.

- `AUTO_MATCHED`
- `CANDIDATE_MATCHED`
- `MANUAL_MATCHED`
- `UNMATCHED`
- `EXPECTED_ONLY`
- `RECEPTION_ONLY`

## 반품처리 작업 상세 흐름

기본 흐름은 다음과 같다.

```text
운송장 또는 입고번호 스캔
→ 고객사/반품예정/업체접수 참고정보 조회
→ 상품 스캔 또는 상품 선택
→ 수량 확인
→ 판정 선택
→ 목적 창고 자동 추천
→ 사진/메모 입력 후보
→ 반품관리번호/라벨 정책 적용
→ 처리완료
→ 재고 이벤트 후보 또는 READY 상태 생성
```

## 운송장 조회 결과 케이스

| 케이스 | 작업자 화면 동작 | 정책 |
| --- | --- | --- |
| 반품예정자료와 업체접수자료가 모두 있음 | 예정자료와 접수자료를 함께 참고정보로 표시하고 상품/수량/판정은 작업자가 확정한다. | 두 자료의 상품정보는 후보이며 확정값이 아니다. |
| 반품예정자료만 있음 | 운송장 기준 예정 정보를 표시하고 실제 상품 스캔을 요구한다. | 업체 접수자료가 없어도 처리 가능하다. |
| 업체접수자료만 있음 | 업체 요청 정보를 참고로 표시하고 실제 도착 여부와 상품을 확인한다. | 접수자료만으로 재고 반영하지 않는다. |
| 둘 다 없음 | 수동 처리 후보로 전환하고 고객사/상품 확인을 요구한다. | 고객사/상품이 확인되지 않으면 미확인 보관/보류 대상으로 둔다. |
| 이미 처리 완료된 운송장 | 기존 처리 결과를 표시하고 중복 처리 액션을 차단한다. | 정정은 별도 권한/정정 흐름으로 분리한다. |
| 복수 후보가 있는 운송장 | 후보 목록을 표시하고 선택 또는 관리자 확인으로 보낸다. | 자동 선택으로 확정하지 않는다. |

공통 정책은 다음과 같다.

- 둘 다 없어도 고객사/상품이 현장에서 확인되면 수동 처리 후보가 될 수 있다.
- 고객사/상품이 확인되지 않으면 정상 등록하지 않고 미확인 보관/보류 대상으로 둔다.
- 이미 처리 완료된 운송장은 중복 처리를 차단한다.
- 복수 후보는 후보 선택 또는 관리자 확인이 필요하다.

## 상품 확인

- 상품 스캔은 `ProductScanMatchService` 기준을 따른다.
- `client_id` 범위 안에서만 상품을 찾는다.
- 상품코드, 대표바코드, 추가바코드를 모두 지원한다.
- `product_barcodes.unit_qty`는 수량 반영에 사용한다.
- 미등록 상품은 바로 재고 반영하지 않는다.

## 판정 상태

1차 MVP 판정 후보는 다음과 같다.

| 판정 상태 | 의미 | 후속 흐름 |
| --- | --- | --- |
| `GOOD` | 정상재고 복귀 후보 | 재고 이벤트 후보로 분리하고 기본 라벨은 출력하지 않는다. |
| `HOLD` | 확인 필요 또는 정책 보류 대상 | 보류 창고 이동 후보이며 설정에 따라 라벨 출력 가능하다. |
| `DISPOSAL` | 폐기 대상 | 기본 수량 확인 중심이며 필요 시 라벨 선택 출력 가능하다. |
| `REFURB_A` | 리퍼 A 등급 대상 | 반품관리번호를 부여하고 추적/반출 대상으로 둔다. |
| `REFURB_B` | 리퍼 B 등급 대상 | 반품관리번호를 부여하고 추적/반출 대상으로 둔다. |
| `REFURB_C` | 리퍼 C 등급 대상 | 반품관리번호를 부여하고 추적/반출 대상으로 둔다. |
| `MANUFACTURER_RETURN` | 제조사반품 대상 | 반품관리번호를 부여하고 외부반출 대상으로 둔다. |
| `SAMPLE` | 샘플 또는 별도 회수 대상 | 반품관리번호를 부여하고 추적/반출 대상으로 둔다. |

정책은 다음과 같다.

- `GOOD`은 정상재고 복귀 후보다.
- `REFURB_A`, `REFURB_B`, `REFURB_C`, `MANUFACTURER_RETURN`, `SAMPLE`은 추적/반출 대상이다.
- `HOLD`는 정책에 따라 라벨 출력 또는 보류 창고 이동 대상이다.
- `DISPOSAL`은 기본 수량 확인 중심이며, 필요 시 라벨 선택 출력 가능하다.

## 목적 창고 추천

- 고객사별 사용창고와 판정별 라우팅 기준으로 목적 창고를 자동 추천한다.
- 자동 추천은 작업자 편의를 위한 기본값이며, 작업자는 권한에 따라 변경 가능해야 한다.
- 변경 시 변경 사유/이력 기록 후보를 둔다.

## 라벨/반품관리번호 정책

- 양품은 기본 라벨 미출력이다.
- `REFURB_A`, `REFURB_B`, `REFURB_C`, `MANUFACTURER_RETURN`, `SAMPLE`은 기본 라벨 출력이다.
- `HOLD`와 `DISPOSAL`은 설정값에 따라 기본 출력 여부를 정한다.
- 라벨 출력 실패는 판정 저장 실패가 아니다.
- 재출력은 기존 반품관리번호를 다시 출력하는 것이며 새 번호를 만들지 않는다.

## 반품 마감 상세 흐름

기본 흐름은 다음과 같다.

```text
기간/고객사/판정상태 조회
→ 판정 완료 대상 목록 표시
→ 상태별 수량 대조
→ 차이 확인
→ 보류/재확인/마감확정
```

정책은 다음과 같다.

- 반품 마감은 새로운 판정을 하는 화면이 아니다.
- 반품 마감은 구글시트 동기화 화면이 아니다.
- 양품/폐기는 상품바코드 기준 수량 대조다.
- 리퍼/제조사반품/샘플/보류는 반품관리번호 기준 1:1 대조다.
- 마감확정 전 차이가 있으면 확정하지 않는다.
- 마감 후 정정은 별도 권한/정정 흐름으로 분리한다.

## 반품 반출 상세 흐름

기본 흐름은 다음과 같다.

```text
외부반출 대상 조회
→ 반출 묶음 생성
→ 반품관리번호 스캔
→ 대상 전량 대조
→ 반출확정
→ 재고 이벤트 생성 후보
```

대상은 다음과 같다.

- `REFURB_A`
- `REFURB_B`
- `REFURB_C`
- `MANUFACTURER_RETURN`
- `SAMPLE`
- `HOLD` 중 외부반출 대상

정책은 다음과 같다.

- 반품 반출은 반품처리 작업이나 마감 화면에 넣지 않는다.
- 반출확정은 판정 변경이 아니다.
- 반출확정 후 재고 차감은 서버 `inventory_events` 경로에서 처리한다.
- 반품관리번호 중복 스캔을 차단한다.

## 반품 통합추적

반품 통합추적은 읽기 전용 조회 화면이다. 조작 화면이 아니다.

조회 기준은 다음과 같다.

- 운송장번호
- 원송장번호
- 반품관리번호
- 고객사
- 상품코드/바코드
- `external_ref_no`
- `work_batch_id`
- 기간

표시 후보는 다음과 같다.

- 접수자료
- 예정자료
- 처리결과
- 판정
- 라벨
- 마감
- 반출
- 재고 이벤트
- 구글시트 회신 상태

금지 항목은 다음과 같다.

- 판정 변경
- 마감확정
- 반출확정
- 구글시트 push 실행
- 재고 재처리

## DB/API 설계 전 주의사항

- 이 문서는 구현 지시가 아니라 업무흐름 기준 문서다.
- 이 문서 이후 DB 컬럼/API 상세를 설계한다.
- `return_expected_rows`, `vendor_return_rows`, `return_receipts`, `return_receipt_items`, `return_units`, `return_closing_sessions`, `return_external_outbound_batches` 관계는 후속 DB 상세 문서에서 확정한다.
- 반품처리 작업 중 재고를 직접 변경하지 않는다.
- 재고 반영은 `inventory_events` 기준 서버 흐름에서 처리한다.
- `scan_events`는 스캔 이벤트 로그이며 재고 원장이 아니다.

## Codex 구현 전 체크

- 이 화면이 반품자료 준비/반품처리/반품 마감/반품 반출/통합추적 중 어디에 속하는가?
- 구글시트 동기화를 반품처리 화면에 넣고 있지 않은가?
- `batch_id`를 업무 처리 중심키로 쓰고 있지 않은가?
- 반품예정 상품정보를 최종 확정값으로 쓰고 있지 않은가?
- 실제 상품/수량/판정은 반품처리 작업에서 확정되는가?
- 라벨 출력 실패가 판정 저장 실패로 이어지지 않는가?
- 재고를 직접 변경하지 않고 `inventory_events` 흐름으로 연결되는가?
- 작업자 화면과 관리자 화면을 섞고 있지 않은가?
