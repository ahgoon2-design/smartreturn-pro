# SmartReturn Pro 반품처리 작업순서 및 게이트 참조문서

> 성격: 이 문서는 **규칙 파일이 아니라 작업 참조문서**다.
> `AGENTS.md`, `ai-harness/memory/000-read-this-first.md`, 그 외 memory/하네스 규칙을 **대체하지 않는다.**
> 충돌이 있으면 `AGENTS.md`의 보안·중단 조건·문서 언어 규칙이 항상 우선한다.
> 이 문서는 반품처리 작업을 시작할 때 Claude Code, Codex, ChatGPT가 **함께 보는 기준 문서**다.

---

## 1. 문서 목적

- 반품처리 작업에서 **검수 → 보강 → SPEC → 구현 → 검수 → 커밋** 순서가 매번 흔들리지 않도록 고정한다.
- Claude(채팅), Claude Code, Codex, ChatGPT가 **같은 기준**으로 "지금 무엇을 하는 단계인지"와 "SPEC이 필요한지"를 판단하도록 한다.
- 다시 강조한다. **이 문서는 규칙 파일이 아니라 작업 참조문서다.** 규칙의 최종 권위는 `AGENTS.md`와 memory에 있다.

이 문서가 막으려는 반복 오해는 세 가지다.

1. 반품 검수(반품 모듈 스코프)와 전 모듈 공통 격리 구조(deny-by-default / RLS / 중앙화)는 **다른 트랙**이라는 점.
2. 이번 검수는 SPEC이 아니라 **read-only 탐색**이며, 보강이 로직변경이면 **구현 전 SPEC이 먼저** 필요하다는 점.
3. read-only 검수 범위는 **우선순위 1 + 2로 한정**하고, **UX/Help는 후속 작업**으로 분리한다는 점.

---

## 2. 현재 기준

- SPEC-003은 반품처리 주요 화면 **7개**와 스캔우선(scan-first) UX/레이아웃의 **1차 구현·검증이 완료된 상태**다.
- SPEC-003은 **실운영 반품처리 완성이 아니다.** 화면/UX 1차 구현 완료 단계일 뿐이다.
- 판정(judgment), 처리완료, 보류(HOLD), 폐기, 외부반출, 일마감, 재고반영 같은 **업무 DB 쓰기 흐름**은 별도 검수/보강이 필요하다.
- 따라서 **현재 다음 단계는 새 화면 추가가 아니라**, 반품 업무 흐름의 **연결 상태와 정합성 검수**다.

---

## 3. 작업 트랙 구분

반품처리 작업은 반드시 아래 두 트랙을 **분리해서** 쓴다. 한쪽 트랙의 결과로 다른 트랙을 끝낸 것으로 판단하지 않는다.

### 3.1 반품처리 모듈 트랙

이번 반품 검수가 보는 스코프다. 범위:

- 접수/수집 자료 (업체 반품접수, 채널 수집 자료)
- CJ 반품/배송 자료 (반품예정 자료)
- 센터 입고 스캔
- 반품 매칭
- 고객사 / 운영단위 / 창고 범위 (`client_id` / `client_unit_id` / `warehouse_id`)
- 판정
- 처리완료
- HOLD / 보류
- 폐기
- 외부반출
- 일마감
- 재고반영

### 3.2 전 모듈 공통 격리 구조 트랙

반품 모듈에 국한되지 않는 플랫폼 전체 격리 구조다. 범위:

- deny-by-default (기본 거부)
- RLS 또는 그에 준하는 **중앙화 격리 구조**
- role / data scope / feature gate 분리
- 백엔드 공통 데이터 범위 강제
- 반품 외 모듈 전체의 권한·테넌트 격리

명시:

- 이 트랙은 **사라진 것이 아니다.**
- 현재 반품 검수에서는 **미확인으로 남긴다.**
- 별도 **구조 SPEC**으로 진행해야 한다.
- 반품 엔드포인트만 수동으로 막는 방식은 **장기 해법이 아니다.** 반품 엔드포인트 수동 차단만으로 전체 플랫폼 보안을 끝낸 것으로 판단하지 않는다.

---

## 4. read-only 검수 범위

이번 반품처리 **read-only** 검수 범위는 아래 **우선순위 1 + 2** 두 개만 포함한다.

### 우선순위 1: 실제 업무 흐름 연결 상태

확인 항목:

- 접수/수집 자료에서 반품 처리로 이어지는가
- CJ 반품/배송 자료와 매칭되는가
- 센터 입고 스캔 흐름이 실제 데이터와 연결되는가
- 고객사 / 운영단위 / 창고 범위(`client_id` / `client_unit_id` / `warehouse_id`)가 누락되지 않는가
- 판정 / 처리완료 / 보류 / 폐기 / 외부반출 / 일마감 / 재고반영 흐름이 **어디까지 구현되어 있는가**
- **화면만 있는 상태인지, API가 연결되어 있는지, DB 쓰기가 발생하는지**를 구분한다

### 우선순위 2: 쓰기 액션별 정합성

확인 항목:

- API가 backend에서 데이터 범위를 강제하는가
- `client_id` / `client_unit_id` / `warehouse_id`가 누락되지 않는가
- `role` 기준 권한이 적용되는가
- 고객사 사용자가 다른 고객사 데이터를 건드릴 수 없는가
- **처리완료 시 `current_inventory`가 바뀌지 않는가** (처리완료 시 `current_inventory` 변경 금지)
- **처리완료 시 `inventory_events`가 생성되지 않는가** (처리완료 시 `inventory_events` 생성 금지)
- 마감/확정 이후에만 재고 이벤트(`inventory_events`)가 생성되는가
- 같은 건을 두 번 확정할 수 없는가
- 중복 마감 / 중복 반출 / 중복 폐기 / 중복 재고반영이 차단되는가
- OVER / 초과 이력이 삭제·무시되지 않고 **확인필요 건으로 분리**되는가

---

## 5. read-only 검수 제외 범위

아래는 이번 read-only 검수 범위가 **아니다.**

- UX 보강
- 버튼 배치 개선
- 화면 문구 개선
- Help 파일 작성
- 도움말 registry 연결
- 새 화면 추가
- 새 API 구현
- DB migration
- seed 실행
- 업무 DB 쓰기 액션 실행

명시:

- **UX/Help는 read-only 검수 결과에서 후속 작업으로 분리한다.**
- 검수 보고서에 UX/Help 필요성이 발견되면 **"후속 UX/Help 작업 후보"로만 기록**한다.
- read-only 검수 중 UX/Help 작업을 같이 수행하지 않는다.

## 6. SPEC 필요 여부 판단 게이트

**핵심 게이트: "로직변경이면 SPEC 먼저."**
보강 범위 확정 다음에 곧바로 구현으로 가면 안 된다. 단순 버그수정인지 SPEC이 필요한 로직변경인지는 **read-only 검수 보고를 보고 판단**한다.

### 6.1 SPEC 없이 가능한 경우

아래는 SPEC 없이 단순 보강으로 가능할 수 있다.

- 명백한 오타 수정
- 화면 표시 문구의 단순 정정
- 기존 의도와 다른 잘못된 호출 제거
- 처리완료 시 잘못 호출되는 재고변경 함수 제거
- 누락된 방어 조건 추가가 **기존 정책을 명확히 구현하는 수준**인 경우
- 테스트 / 검수 보고서 보강

단, 이 경우에도 구현 전 보고서에서 **"SPEC 불필요 사유"를 명시**해야 한다.

### 6.2 SPEC이 필요한 경우

아래는 구현 전 **별도 SPEC이 필요하다.**

- 쓰기 액션 신규 구현
- 판정 / 처리완료 상태전이 변경
- 보류 / HOLD 상태전이 변경
- 폐기 확정 로직 신규/변경
- 외부반출 확정 로직 신규/변경
- 일마감 로직 신규/변경
- 월마감 로직 신규/변경
- 재고반영 로직 신규/변경
- `inventory_events` 생성 정책 변경
- `current_inventory` 반영 정책 변경
- API 계약(contract) 변경
- DB schema / migration 변경
- 권한 / 데이터 범위 구조 변경
- 전 모듈 공통 deny-by-default / RLS / 중앙화 격리 구조작업
- 고객사 / 운영단위 / 창고 계층 정책 변경

## 7. 고정 작업순서

반품처리 작업은 아래 순서로 진행한다.

1. 인계문 확인
2. `AGENTS.md` 확인
3. `ai-harness/memory/000-read-this-first.md` 확인
4. `ai-harness/handoff/latest-handoff.md` 확인
5. 이 문서 확인 — `docs/process/return-processing-workflow-gate-reference.md`
6. read-only 검수 지시
7. read-only 검수 보고
8. ChatGPT가 보강 범위 판단
9. 아래 중 하나로 분기
   - 단순 버그수정이면 SPEC 없이 보강 지시 가능
   - 로직변경이면 SPEC 작성 먼저
   - 전 모듈 격리 구조면 별도 구조 SPEC으로 분리
   - UX/Help면 별도 UX/Help 작업으로 분리
10. 구현은 Claude Code가 수행
11. 최종 독립 검수는 Codex가 수행
12. 검수 통과 후 Codex 수문장 커밋
13. 사용자 별도 승인 후 push

## 8. 보고서 필수 문구

read-only 검수 보고에는 아래 문구가 **반드시** 들어가야 한다.

- "이번 검수는 반품처리 모듈 스코프만 확인했다."
- "반품 외 모듈의 deny-by-default / RLS / 중앙화 격리 구조는 미확인이다." (**반품 외 모듈 스코프는 미확인**)
- "전 모듈 공통 격리 구조는 별도 구조 SPEC으로 보류한다."
- "이번 검수는 SPEC이 아니라 read-only 탐색이다."
- "보강이 단순 버그수정인지, 로직변경으로 SPEC이 필요한지는 본 보고 기준으로 별도 판단해야 한다."
- "UX/Help는 이번 read-only 검수 범위가 아니며 후속 작업으로 분리한다." (**UX/Help는 후속 작업**)

## 9. 중단 조건

아래 중 하나라도 발견되면 검수/작업을 **중단하고 보고**한다.

- 반품 모듈 검수 중 전 모듈 격리 구조 변경이 필요해지는 경우
- 쓰기 액션 신규/변경이 필요한데 SPEC 없이 구현하려는 경우
- seed / migration / API 변경이 필요한데 읽기전용 검수 범위를 넘는 경우
- 반품 외 모듈까지 범위가 번지는 경우
- UX/Help 작업이 read-only 검수에 섞이는 경우
- 업무 DB 쓰기 실행이 필요한 경우
- secret / local / settings 확인이 필요한 경우

---

## 10. 최종 판단 문장

> SmartReturn Pro 반품처리는 **화면 구현 완료 여부**와 **실운영 업무 흐름 완성 여부**를 분리해서 판단한다.
> SPEC-003은 **화면/UX 1차 구현 완료 단계**이며, 실제 판정·처리완료·마감·재고반영 흐름은 **read-only 검수 후 단순 버그수정인지 SPEC 필요한 로직변경인지 나누어** 진행한다.
> 전 모듈 공통 **deny-by-default / RLS / 중앙화 격리 구조**는 반품 모듈 검수와 **별도 트랙으로 보류**하며, **사라진 작업으로 취급하지 않는다.**
