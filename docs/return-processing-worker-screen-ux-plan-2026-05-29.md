# 반품처리 작업 화면 UX 계획

## 1. 문서 목적

이 문서는 SmartReturn Pro의 반품처리 작업 화면을 구현하기 전에 작업자 UX와 화면 구조를 확정하기 위한 기준이다.

기존 SmartReturn 반품처리 루틴에서 배운 운송장 스캔 중심 흐름, 실제 자료 그리드 중심 화면, 우측 가로 스크롤 문제를 SmartReturn Pro 공통 컴포넌트 기준으로 재구성한다. 특히 `SmartDataGrid`의 크기와 모양 통일, 우측 가로 스크롤 보장, 작업자용 단순 흐름을 다음 skeleton 구현 전에 고정한다.

## 2. 화면 성격

- 반품처리 작업 화면은 관리자 조회 화면이 아니라 작업자용 현장 처리 화면이다.
- 작업자는 운송장을 빠르게 스캔하고, 대상 row를 확인하고, 상품을 스캔하거나 확인한 뒤 판정하고 완료해야 한다.
- 복잡한 검색 조건, 통계 카드, 관리자용 필터는 최소화한다.
- 스캔 입력, 현재 처리 대상, 다음 처리 대상, 오류 피드백이 가장 잘 보여야 한다.
- 화면의 중심은 반품처리 대상 그리드이며 안내문이나 카드가 그리드를 밀어내면 안 된다.

## 3. 1차 작업 흐름

1차 기준 흐름은 다음과 같다.

1. 운송장 스캔
2. `READY_FOR_PROCESSING` 대상 조회
3. 해당 운송장, 주문, 상품 목록 표시
4. 상품 확인 또는 바코드 스캔
5. 판정 선택
6. 메모와 사진 필요 여부 표시 또는 placeholder
7. 라벨 출력 여부 표시 또는 placeholder
8. 처리 완료 placeholder

1차 skeleton에서는 판정 저장, 사진 업로드, 라벨 출력, 재고 반영까지 구현하지 않는다. 화면 구조와 `GET /api/returns/processing/tasks` 기반 조회 흐름을 먼저 구현한다.

## 4. 추천 화면 레이아웃

1366x768 기준 추천 구조는 다음과 같다.

- 상단 고정 영역: 큰 운송장 스캔 입력, 조회 상태, 간단한 처리 요약
- 중앙 영역: 반품처리 대상 `SmartDataGrid`
- 우측 또는 하단 영역: 선택 row 상세와 판정 placeholder 패널
- 하단 영역: 최근 처리 로그 또는 주요 action 영역

주의 기준:

- 카드 남발 금지
- 안내문 과다 금지
- 그리드가 화면의 중심이어야 함
- 주요 action 버튼은 항상 보이거나 찾기 쉬운 위치에 있어야 함
- 상단 입력과 하단 action 때문에 그리드 첫 화면이 과하게 줄어들면 안 됨

## 5. 그리드 설계 기준

- 모든 목록은 `SmartDataGrid`를 사용한다.
- 우측 가로 스크롤 노출을 보장한다.
- 컬럼 최소폭을 보장하고 필요한 컬럼을 좁게 압축하지 않는다.
- row 높이, header 높이, font size, cell padding은 `SmartDataGrid` 기준을 따른다.
- 상태는 `SmartStatusBadge` 계열로 통일한다.
- 운송장번호, 주문번호, 상품코드, 바코드는 copyable cell로 둔다.
- `row_no` 또는 접수 원본 순서를 보존한다.
- 선택 row를 명확히 강조한다.
- 다음 처리 대상 row 강조는 1차 skeleton 이후 후보로 둔다.
- 1366x768에서 그리드는 남은 높이를 차지하고 내부 스크롤을 가진다.
- 라벨, 사진, 판정 관련 우측 컬럼이 화면 밖으로 사라지지 않도록 그리드 내부 가로 스크롤 컨테이너를 확인한다.

## 6. 1차 컬럼 후보

반품처리 대상 그리드의 1차 컬럼 후보는 다음과 같다.

- 상태
- `row_no`
- 운송장번호
- 주문번호
- 상품코드
- 바코드
- 상품명
- 옵션명
- 수량
- 반품사유
- 검증상태
- 작업상태
- 판정
- 메모
- 사진
- 라벨

1차 skeleton에서는 판정, 메모, 사진, 라벨은 placeholder 컬럼 또는 후속 표시로 둬도 된다. 실제 저장과 출력은 다음 단계에서 별도 구현한다.

## 7. 스캔 입력 기준

- 화면 진입 시 운송장 스캔 입력에 focus를 둔다.
- Enter 또는 스캐너 입력 후 자동 조회한다.
- 조회 결과가 1건이면 자동 선택 후보로 둔다.
- 여러 건이면 첫 번째 미처리 row를 강조하는 후보로 둔다.
- 조회 실패 시 작업자가 바로 알 수 있는 큰 오류 메시지를 표시한다.
- 조회 성공 시 현재 대상과 다음 행동을 짧게 표시한다.
- 작업자가 마우스로 검색, 필터, 선택을 반복하지 않도록 한다.

## 8. 판정 패널 기준

1차 skeleton에서는 판정을 저장하지 않고 방향만 고정한다.

판정 후보:

- 양품
- 리퍼
- 샘플
- 제조사반품
- 폐기
- 보류

장기적으로 판정 값은 상품군, 고객사, 공통코드, 판정 정책을 따라야 한다. 화면 내부 하드코딩은 1차 skeleton의 placeholder 수준을 넘기지 않는다.

## 9. 사진/라벨 기준

1차 skeleton에서는 사진과 라벨을 placeholder로 둔다.

- 사진은 판정 데이터의 일부로 본다.
- 사진은 나중에 별도 등록하는 기능이 아니라 판정 시 함께 등록하는 방향을 유지한다.
- 라벨은 상태별 기본 출력 정책을 따른다.
- 양품은 기본 라벨 출력 대상이 아니다.
- 리퍼, 제조사반품, 샘플, 보류 등 추적 대상은 라벨 출력 대상 후보다.
- 실제 출력은 Local Agent 연동 단계에서 처리한다.
- 라벨 출력 실패가 판정 저장 실패로 이어지지 않도록 별도 흐름으로 분리한다.

## 10. 상태 전환 기준

1차 skeleton 기준 상태 흐름은 다음 후보를 따른다.

- `READY_FOR_PROCESSING`: 반품처리 대기 대상
- `PROCESSING`: 스캔 또는 선택 후 처리 중 후보
- `COMPLETED`: 판정 완료 후 후보
- `HOLD`: 보류 후보

이번 문서에서는 상태 전환 API를 구현하지 않는다. 다음 구현에서는 `READY_FOR_PROCESSING` 조회와 선택까지만 연결하고, 저장형 상태 전환은 후속 범위로 둔다.

## 11. 기존 SmartReturn 참고 결과

직접 참고 후보였던 `ReturnIntakeScreen`, `ReturnConfirmationWorkspace`는 접근 가능한 기존 SmartReturn 저장소에서 파일을 확인하지 못했다. 대신 현재 저장소에 남아 있는 SmartReturn Pro 반품 설계 문서와 구현을 참고 기준으로 사용했다.

참고한 문서와 파일:

- `docs/ui/smartreturn-pro-return-screen-design.md`
- `docs/ui/smartreturn-pro-return-field-column-map.md`
- `docs/business/smartreturn-pro-return-api-policy.md`
- `docs/skills/worker-screen-ux.md`
- `frontend/src/features/returns/ReturnIntakeHubPage.tsx`
- `frontend/src/components/grid/SmartDataGrid.tsx`
- `backend/app/routers/returns.py`

가져올 기준:

- 운송장 기준으로 실제 도착 반품을 조회한다.
- 상품코드, 바코드, 상품명, 수량, 판정, 라벨 상태를 그리드에서 확인한다.
- 작업자 화면은 스캔과 현재 대상 확인을 우선한다.
- 페이지 전체 가로 스크롤이 아니라 그리드 내부 가로 스크롤을 사용한다.
- 처리 화면에 구글시트 동기화, 업로드, 이력, 정산, 마감 기능을 섞지 않는다.

반복하지 말아야 할 문제:

- 우측 가로 스크롤이 보이지 않아 라벨, 사진, 판정 컬럼을 못 보는 문제
- 안내 카드가 많아 실제 작업 그리드가 작아지는 문제
- 탭, 필터, 버튼이 많아 스캔 흐름이 끊기는 문제
- 화면마다 행 높이, 버튼 위치, 줄맞춤이 달라지는 문제

SmartReturn Pro 적용 방식:

- 기존 화면을 복사하지 않고 `SmartPage`, `SmartPageHeader`, `SmartDataGrid`, `SmartStatusBadge`, sticky action 영역 기준으로 재구성한다.
- 실제 처리 원장은 접수 row가 아니라 반품처리 작업 흐름에서 확정한다.
- `batch_id`는 추적 보조키이며 작업 화면의 중심키로 쓰지 않는다.

## 12. 1차 skeleton 구현 범위

다음 작업에서 구현할 범위는 다음으로 제한한다.

- `/returns/processing` route 추가
- 메뉴명: 반품처리 작업
- 운송장 스캔 입력
- `GET /api/returns/processing/tasks` 조회 연결
- `SmartDataGrid`로 `READY_FOR_PROCESSING` 목록 표시
- 운송장번호 검색 또는 필터
- row 선택 상세 패널
- 판정, 사진, 라벨은 placeholder
- 저장 API는 아직 연결하지 않음

## 13. 구현하지 않을 것

다음 항목은 1차 skeleton 범위가 아니다.

- 판정 저장
- 사진 업로드
- 라벨 출력
- 재고 반영
- 일마감
- 외부반출
- 정산
- 상품군별 복잡 판정
- Local Agent 연동
- 반품 접수 Excel 업로드
- 외부 쇼핑몰 또는 택배사 API 연동

## 14. Closeout 결론

다음 작업은 목표추진 모드로 반품처리 작업 화면 skeleton 구현을 진행한다.

구현 시 기존 SmartReturn 참고 기준을 그대로 복사하지 않고, SmartReturn Pro 공통 UI 기준으로 재구성한다. 특히 `SmartDataGrid` 우측 가로 스크롤, 컬럼 최소폭, 1366x768 화면 높이, 작업자용 스캔 중심 흐름을 반드시 지킨다.
