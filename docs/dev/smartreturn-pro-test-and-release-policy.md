# SmartReturn Pro 테스트 및 릴리스 정책

이 문서는 SmartReturn Pro 신규 제작 기준이다. 기존 SmartReturn의 구현기록, 빌드 방식, 배포 관행을 그대로 따르지 않는다.

## 자동 테스트 기준

- 변경 범위에 맞는 자동 테스트를 우선 실행한다.
- DB, import, 권한, 재고 반영처럼 위험도가 높은 변경은 테스트 범위를 넓힌다.
- 스캔, Local Agent, 프린터, 사운드 관련 기능은 저장 흐름과 장치 흐름을 분리해 검증한다.
- 테스트가 없으면 최소한 검증 가능한 수동 확인 절차를 보고한다.

## 수동 테스트 기준

- 화면 작업은 1366x768 기준 핵심 입력, 그리드 첫 5행, 우측 패널, 하단 액션바가 보이는지 확인한다.
- 반품, 입고, 출고는 자료 준비와 실제 처리, 확정 흐름이 섞이지 않았는지 확인한다.
- 권한 작업은 내부 운영자와 고객사 사용자를 `role` 기준으로 구분해 확인한다.
- 재고 작업은 `scan_events`와 `inventory_events`가 분리되어 있는지 확인한다.

## 빌드 기준

- 빌드는 사용자가 요청하거나 변경 검증에 필요한 경우 실행한다.
- 빌드 산출물은 커밋하지 않는다.
- ERP 실제 API는 초기 테스트에서 제외한다.
- Local Agent는 실제 장치 제어보다 `DRY_RUN` 우선으로 검증한다.

## 커밋 전 점검

- `git diff --check`를 실행한다.
- `config.json`, `logs`, `outputs`, `dist`, `build`, `zip`, `exe`, `__pycache__`, `.env`를 커밋하지 않는다.
- 민감정보, 접속정보, 실제 운영 계정 정보가 포함되지 않았는지 확인한다.
- 문서 변경은 한글 본문 규칙을 지켰는지 확인한다.

## 커밋 원칙

- 커밋은 사용자가 명시하기 전 금지한다.
- 사용자가 커밋을 요청하면 변경 범위와 제외 파일을 먼저 확인한다.
- 관련 없는 파일 변경은 커밋 범위에 포함하지 않는다.

## 테스트 미실행 보고

- 테스트를 실행하지 못했거나 실행하지 않은 경우 사유를 보고한다.
- 실행하지 않은 테스트가 남긴 위험요소를 함께 보고한다.
- 검증 가능한 대체 확인을 수행했다면 그 결과를 보고한다.

## Codex 구현 전 체크

- 변경 범위에 맞는 자동 테스트 또는 수동 검증 계획이 있는가?
- Local Agent 기능은 `DRY_RUN` 우선으로 검증하는가?
- ERP 실제 API를 초기 테스트에 포함하지 않았는가?
- `git diff --check`를 실행했는가?
- 커밋 금지 파일과 민감정보를 확인했는가?
- 커밋을 사용자가 명시적으로 요청했는가?
