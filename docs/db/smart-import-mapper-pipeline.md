# Smart Import Mapper / 저장전검증 UX 기준

이 문서는 Smart Import Mapper와 저장전검증 화면을 구현하기 전 확인할 UX/검증 기준이다. 이번 문서는 화면 구현 지시가 아니라 설계 기준이다.

## 기본 원칙

- import job과 실제 업무 테이블을 분리한다.
- 원본보기, 수정보기, 검증결과보기 상태를 구분한다.
- 저장 전 검증은 사용자가 무엇을 고쳐야 하는지 구체적으로 보여줘야 한다.
- 노란 안내카드는 닫기/접기 가능해야 하며 화면을 계속 가리면 안 된다.

## 같은 운송장 여러 상품

같은 운송장에 여러 상품이 있다고 해서 무조건 확인필요가 아니다.

출고도 합포장이고 반품도 나간 만큼 들어온 경우 정상일 수 있다.

판단 기준:

- 원주문/원송장에 다상품 출고가 있었는가?
- 반품 접수자료에도 다상품이 존재하는가?
- 상품 수량 합계가 출고/접수와 맞는가?
- 고객사 정책상 합포장이 허용되는가?

정상 후보이면 “확인필요” 대신 “다상품 정상 후보”처럼 표시한다.

## 기존 저장자료 중복

기존 저장자료와 중복될 때는 오류만 표시하지 않는다. 상황에 따라 아래처럼 나눈다.

- 이미 저장됨.
- 중복 후보.
- 재등록 확인.
- 값 변경 후보.

중복이 업무상 허용되지 않는 경우에는 저장을 막되, 왜 막혔는지 기준 컬럼을 보여준다.

## 기존 저장자료와 값이 다른 경우

“기존 저장자료와 값이 달라 확인이 필요합니다”만 보여주면 안 된다.

반드시 어떤 컬럼이 다른지 보여준다.

예시:

| 컬럼 | 기존 값 | 업로드 값 |
| --- | --- | --- |
| 상품코드 | A001 | A002 |
| 수량 | 1 | 2 |
| 반품사유 | 단순변심 | 파손 |

## 컬럼매핑 수정 후 재검증

컬럼매핑 수정 실행 후에는 아래를 보여준다.

- 변경 전 매핑.
- 변경 후 매핑.
- 재검증 범위.
- 재검증 결과.
- 저장 가능/확인필요/오류 건수 변화.

사용자가 “무엇이 바뀌었고 왜 저장 가능해졌는지”를 이해할 수 있어야 한다.

## 화면 상태 구분

- 원본보기: 업로드 원본을 읽기 전용으로 보여준다.
- 수정보기: 매핑 또는 보정 가능한 필드만 수정한다.
- 검증결과보기: 오류, 경고, 중복 후보, 저장 가능 상태를 보여준다.

상태가 섞이면 사용자가 원본을 바꾸는지, 저장 전 보정값을 바꾸는지 알 수 없다.

## 문구 원칙

- 내부 enum이나 DB 필드명만 보여주지 않는다.
- 오류 문구는 원인, 영향, 다음 행동을 포함한다.
- 안내문은 짧게 쓰고, 상세 설명은 접히는 영역으로 둔다.

## Codex 구현 전 체크

- 같은 운송장 다상품을 무조건 오류로 처리하지 않는가?
- 중복을 “오류” 하나로만 표현하지 않는가?
- 기존 값과 업로드 값의 차이를 컬럼 단위로 보여주는가?
- 컬럼매핑 수정 후 재검증 결과를 명확히 보여주는가?
- 원본보기/수정보기/검증결과보기가 구분되는가?
