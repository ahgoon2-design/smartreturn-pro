# 똘고리 / Self-Fix Loop

## 1. 정체

똘고리는 SmartReturn Pro 똘망이 안에서 **지시문 생성 단계에 적용하는 자가수정루프**다.

똘고리는 작업 실행기가 아니다. 코드 수정기가 아니다. Claude가 만든 지시문 초안을 스스로 검수하고 보완해, Claude Code 또는 Codex에 넘길 최종 실행 지시문을 단단하게 만드는 루프다.

기존 SELF-FIX-LOOP의 실행 중 자기테스트/자가수정 3회 원칙은 유지한다. 다만 용어를 분리한다.

- 똘망이: SmartReturn Pro 개발 팀 운영 구조 전체
- 똘고리: 지시문 생성 단계 자가수정루프
- 실행 자가수정 루프: 구현자가 자기테스트로 객관적 실패를 최대 3회까지 고치는 실행 단계 루프

똘고리의 목적은 사용자가 Claude 초안을 ChatGPT에 다시 붙여 검수하고, 다시 Claude에게 보완시키는 수동 왕복을 줄이는 것이다. Claude는 최종 지시문을 내기 전에 똘고리를 적용해 빠진 게이트, 섞인 단계, SPEC 누락, 보안/권한/테넌트/재고/마감/API/DB 위험을 먼저 잡아야 한다.

## 2. 똘고리 입력과 출력

### 입력

똘고리는 지시문 초안을 만들 때 아래 정보를 입력으로 삼는다.

- ChatGPT가 정한 다음 작업 목표
- 대상 저장소와 브랜치
- 실행대상
- 작업 모드: read-only / 문서 작성 / 설계 / 구현 / 검수 / 커밋 수문장 / push
- 작업 범위
- 제외 범위
- 게이트와 중단 조건
- 참고 문서
- 작업 후 정상 dirty 상태
- 완료 보고 형식

### 출력

똘고리 적용 후 Claude는 아래 결과를 최종 지시문에 반영한다.

- 보완된 최종 지시문
- 적용한 보완 요약
- 여전히 남은 위험
- 실행 전 중단 조건
- 똘고리 판정 결과

최종 지시문에는 긴 해설을 붙이지 않는다. 다만 지시문 하단에 똘고리 판정 결과와 핵심 보완 요약을 짧게 남긴다.

## 3. 똘고리 절차

Claude가 지시문을 만들 때는 아래 순서로 처리한다.

1. 초안 작성
   - 작업 목표, 실행대상, 작업 모드, 범위, 제외 범위, 게이트, 검증, 보고 형식을 먼저 채운다.

2. 단계 혼입 검사
   - read-only / 설계 / 구현 / 검수 / 커밋 / push가 한 지시문 안에서 섞였는지 확인한다.
   - 검수 지시문에 코드 수정, API 수정, DB 변경, seed 실행, migration 실행이 들어갔으면 제거하거나 중단한다.
   - 보고서 작성은 문서 산출물 작성과 다르다. 코드 read-only 검수에서도 보고서 작성이 허용되는지, 허용된다면 어떤 dirty가 정상인지 명시한다.

3. SPEC 게이트 검사
   - 쓰기 액션, 상태전이, 마감, 재고, 정산, API 계약, DB schema, migration, 권한/테넌트 구조 변경이면 구현 전 SPEC 필요 여부를 판단한다.
   - 로직변경이면 "SPEC 먼저"를 명시한다.
   - SPEC 없이 가능한 단순 보강이면 그 사유를 지시문에 적는다.

4. 고위험 누락 검사
   - 보안, 로그인, 권한, 테넌트, 데이터 스코프, 반품 쓰기흐름, 재고, 마감, 정산, ERP, API, DB 위험을 점검한다.
   - 필요한 경우 `client_id`, `client_unit_id`, `warehouse_id`, `agency_id`, `role`, feature gate를 명시한다.
   - 반품 처리/재고 작업이면 `current_inventory`와 `inventory_events` 정책을 명시한다.

5. git/dirty 검사
   - 작업 전 `git status --short` 예상치를 적는다.
   - 작업 후 정상 dirty 상태를 적는다.
   - `git add .`, `git add -A`, 무단 commit/push 금지를 넣는다.
   - 커밋 수문장 작업이면 선별 stage 대상 1개 또는 명확한 파일 목록을 적는다.

6. 보안/로컬 파일 검사
   - secret, `.env`, `local.secret.json`, API key, token, password, password_hash, settings 내용 출력 금지를 넣는다.
   - secret 내용을 봐야 진행 가능한 작업이면 실행 금지 또는 사용자 판단으로 돌린다.

7. 완료 보고 검사
   - 변경 파일, 검증 결과, 미실행 항목, 위험요소, 다음 조치가 보고 형식에 들어갔는지 확인한다.
   - 사용자가 text 코드블록 보고를 요구하면 그대로 맞춘다.

8. 판정
   - 아래 판정 결과 중 하나를 최종 지시문에 남긴다.

## 4. 멍청한 루프 금지

똘고리는 형식만 채우고 통과시키는 체크박스가 아니다. 아래 형태는 금지한다.

- "문제 없음"만 쓰고 근거가 없음
- read-only 지시문에 파일 수정 지시가 섞임
- "보고서 작성 허용"과 "코드 read-only"를 구분하지 않음
- SPEC 필요 여부 판단이 없음
- 작업 전/후 git 상태 예상치가 없음
- 정상 dirty 상태가 명시되지 않음
- secret/local/settings 출력 금지가 없음
- 구현자와 최종 검수자 분리가 없음
- commit/push 금지 또는 사용자 승인 조건이 없음
- "되는 것 같다", "아마", "가능해 보임" 같은 추정 표현으로 실행 판단을 대신함
- 파일/라인/명령/문서 근거 없이 위험 판단을 통과시킴
- 반품/재고/권한/테넌트 같은 고위험 작업에서 범위가 섞임
- 검수라고 해놓고 수정, seed, migration, API 변경을 같이 시킴
- consensus-loop와 똘고리를 같은 것으로 설명함

똘고리는 지시문 초안을 더 엄격하게 만드는 장치다. 지시문을 자동 실행하거나 합의 결과를 대신 만들어 주는 도구가 아니다.

## 5. 최종 제출 전 체크리스트

Claude는 최종 지시문을 내기 전에 아래 항목을 확인한다.

- 대상 저장소가 `C:\smartreturn-pro`인지 확인했는가
- SmartReturn Pro와 SmartReturn 본체 `C:\donghyun-logistics-platform`가 섞이지 않았는가
- 실행대상이 Claude Code 또는 Codex 중 정확히 하나인가
- 작업 모드가 명확한가: read-only / 문서 작성 / 설계 / 구현 / 검수 / 커밋 수문장 / push
- read-only면 코드/API/DB/seed/migration 수정 금지가 들어갔는가
- 보고서 작성이 허용되는 경우 정상 dirty 예상 상태가 적혔는가
- SPEC 필요한 작업인지 판단했는가
- 쓰기/마감/재고/상태전이/API 계약/DB 변경이면 SPEC 먼저인지 명시했는가
- 전 모듈 공통 격리 구조와 특정 모듈 검수가 섞이지 않았는가
- 권한/테넌트/스코프 위험이 빠지지 않았는가
- `current_inventory` / `inventory_events` 정책이 필요한 작업이면 명시됐는가
- `git add .` / `git add -A` 금지가 들어갔는가
- push는 별도 승인인지 명시됐는가
- secret/local/settings 출력 금지가 들어갔는가
- 같은 오류 또는 같은 명령 실패 3회 반복 시 중단 조건이 들어갔는가
- 산출물 경로가 명확한가
- 완료 보고 형식이 명확한가

## 7. 똘고리 판정 결과

Claude는 최종 지시문 하단에 아래 중 하나를 명시한다.

- 똘고리 통과: 실행 가능
- 똘고리 보완 후 통과: 실행 가능
- 똘고리 중단: 실행 금지, 이유 보고
- 똘고리 SPEC 요구: 먼저 SPEC 작성 필요
- 똘고리 범위분리 요구: 작업을 나눠야 함

중단, SPEC 요구, 범위분리 요구가 나오면 실행 지시문처럼 포장하지 않는다. 사용자에게 왜 실행하면 안 되는지 보고한다.

## 8. 실행 자가수정 루프

똘고리로 단단해진 지시문을 실제 실행할 때는 기존 실행 자가수정 루프를 따른다.

### 기본 원칙

- 구현자는 자기 작업에 대해 빌드, 테스트, 타입체크, lint, smoke 확인 같은 객관 검증을 직접 수행할 수 있다.
- 객관 검증이 실패하면 같은 세션 안에서 최대 3회까지 자가수정할 수 있다.
- 같은 문제를 3회 고쳐도 해결하지 못하면 4번째 같은 방식으로 반복하지 않는다.
- 3회 실패 시 멈추고 원인, 시도 내역, 남은 위험, 다음 판단 필요 항목을 보고한다.
- 자기가 구현한 작업을 자기가 최종 통과 판정하지 않는다.
- 최종 검수는 구현자가 아닌 다른 쪽이 수행한다.
- 커밋은 수문장 검수와 사용자 승인 후에만 진행한다.

### 실행 흐름

1. 구현
   - 담당자가 코드, 문서, 화면, 테스트를 작성하거나 수정한다.

2. 자기테스트
   - 담당자가 관련 빌드, 테스트, 타입체크, lint, smoke 확인을 직접 수행한다.

3. 자가수정
   - 빨간불이면 원인을 고치고 다시 자기테스트를 수행한다.
   - 같은 문제는 최대 3회까지만 반복한다.

4. 중단 보고
   - 같은 문제를 3회 고쳐도 해결되지 않으면 멈춘다.
   - 실패 원인, 시도한 수정, 남은 문제, 필요한 도움을 보고한다.

5. 구현 완료 보고
   - 자기테스트가 초록불이면 "구현 완료"로 보고한다.
   - 단, 이 보고는 최종 PASS가 아니다.

6. 교차검수
   - 구현자가 아닌 다른 쪽이 독립 검수한다.
   - 보고서를 그대로 믿지 않고 실제 파일, diff, 테스트, build, 권한, 경로, secret, 커밋 후보를 확인한다.

7. 재작업
   - 교차검수에서 빨간불이면 구현자에게 되돌린다.
   - 재작업 루프도 최대 3회 원칙을 따른다.

8. 사용자 인수
   - 교차검수 통과 후 사용자가 화면/흐름/보고를 확인한다.

9. 수문장
   - 커밋 전 Commit Gate를 통과한다.
   - `git status --short`, `git diff --check`, 관련 테스트/build, secret/산출물 제외, 선별 stage 대상 확인을 수행한다.

10. 커밋
   - 사용자가 명시 승인한 뒤에만 관련 파일을 선별 stage/commit한다.
   - push는 별도 승인 후에만 한다.

## 9. 자가검수 허용/금지 경계

### 구현자가 직접 확인해도 되는 것

아래는 기계적·객관적 검증이므로 구현자가 직접 확인할 수 있다.

- 빌드 통과/실패
- 테스트 green/red
- 타입체크 통과/실패
- lint 통과/실패
- import 가능 여부
- 서버 실행 여부
- API 응답 성공/실패
- `git diff --check` 결과
- secret 검색 결과
- 파일 존재 여부
- 브라우저 smoke 확인

### 다른 쪽이 봐야 하는 것

아래는 판단형 검수이므로 반드시 교차검수한다.

- 의도가 맞는가
- 작업 범위를 벗어나지 않았는가
- 빠진 케이스가 없는가
- 권한/테넌시/데이터 범위가 안전한가
- 재고/마감/정산 원칙을 깨지 않았는가
- 고객 화면에 내부 enum/DB 용어가 노출되지 않는가
- 커밋 후보와 제외 파일이 정확한가
- 보고서가 사실과 일치하는가
- 다음 작업으로 넘겨도 되는가

## 10. 역할 배정

### 단계별 실행대상 명확 지정

SmartReturn Pro 작업은 설계, 구축, 검수, 커밋 단계로 분리한다.

- 한 지시문 안에서 설계/구축/검수/커밋을 무리하게 섞지 않는다.
- 각 단계의 실행대상은 지시문마다 Claude Code나 Codex 중 정확히 하나로 지정한다.
- 실행대상을 택일하지 않은 열린 표현으로 쓰지 않는다.
- 구축/수정 단계는 Claude Code나 Codex 중 정확히 하나로 배정할 수 있지만, 사용량이 남은 쪽에 자동 배정하지 않는다.
- 검수 단계는 구현자와 다른 주체에게 별도 지시문으로 배정한다.
- 커밋은 검수 통과 후 별도 Codex 수문장 단계로 진행한다.
- 자기가 구현한 것을 자기가 최종 검수(판단형)하지 않는다.

### ChatGPT

기본 역할:

- 지휘소
- 작업 순서 판단
- 위험도 판단
- Claude Code/Codex 지시문 작성
- 완료 보고 해석
- 다음 작업 큐 결정
- 커밋 범위 판단 보조

### 교차검수 원칙

같은 작업에서 구현자와 최종 검수자는 달라야 한다.

예:

- 클코 구현 -> 코덱 검수
- 코덱 구현 -> 클코 검수

자기가 구현한 것을 자기가 최종 PASS 처리하지 않는다.

## 11. 똘망이 감독 기준

똘고리와 실행 자가수정 루프는 `AGENTS.md`와 ai-harness 규칙을 따른다.

적용 기준:

- 같은 오류 3회 반복 시 중단
- 같은 명령 3회 반복 시 중단
- 브라우저 검증 10~15분 이상 막히면 중단
- dirty 파일 혼입 금지
- 작업 범위 밖 파일 수정 금지
- secret, `.env`, `local.secret`, token, key, password 출력 금지
- `git add .` 금지
- `git add -A` 금지
- 관련 파일만 선별 stage
- commit은 사용자 승인 후
- push는 별도 승인 후
- 빨간불 무마 금지
- 실패를 PASS로 포장 금지
- 스코프 이탈 시 멈춤·보고

## 12. 수문장 연결

똘고리는 커밋 수문장 지시문을 만들 때도 적용한다.

수문장은 자동으로 아무거나 커밋하는 도구가 아니다. 커밋 전 안전 게이트다.

수문장 확인 항목:

- `git status --short`
- `git diff --check`
- 관련 테스트/build 결과
- 변경 파일 목록
- 커밋 후보 파일
- 커밋 제외 파일
- secret/local 설정 제외
- `build/`, `dist/`, `cache/`, `logs/`, `outputs/`, `image/`, `node_modules/`, `.venv/`, `__pycache__/` 제외
- 사용자 승인 여부
- push 별도 승인 여부

## 13. 한계

현재 단계에서 똘고리는 완전 자동 멀티에이전트 루프가 아니다.

- 똘고리는 지시문 생성 단계의 자가수정루프다.
- 실행 자가수정 3회는 각 AI 세션 안에서 수행한다.
- Claude Code <-> Codex 교차검수 전달은 현재 사용자가 수동으로 한다.
- 지시문과 보고서는 사용자가 복붙한다.
- consensus-loop는 지시문/검수지시문/최종판단 생성을 도울 수 있지만, 똘고리 자체가 아니며 Claude Code/Codex를 자동 실행하지 않는다.
- 교차검수 전달 자동화, 훅, 브릿지는 다음 단계 작업이다.

## 14. 완료 판정

똘망이 작업 루프의 완료는 아래 조건을 모두 만족해야 한다.

- 똘고리를 통과한 실행 지시문
- 구현자 자기테스트 초록불
- 교차검수 PASS 또는 조건부 PASS
- 사용자가 필요한 화면/흐름 확인
- 수문장 통과
- 사용자 커밋 승인
- 선별 커밋 완료 또는 커밋 보류 사유 명확화

## 15. 금지

- 지시문 초안을 똘고리 없이 고위험 실행 지시문으로 제출하지 않는다.
- 똘고리를 consensus-loop와 혼동하지 않는다.
- 같은 문제를 4회 이상 같은 방식으로 반복하지 않는다.
- 자기가 구현한 작업을 자기가 최종 PASS 처리하지 않는다.
- 테스트 실패를 무시하지 않는다.
- 빌드 실패를 무마하지 않는다.
- 범위 밖 파일을 몰래 수정하지 않는다.
- dirty 파일을 섞어서 커밋하지 않는다.
- `git add .` 를 사용하지 않는다.
- `git add -A` 를 사용하지 않는다.
- 사용자 승인 없이 commit하지 않는다.
- 별도 승인 없이 push하지 않는다.
- secret, `.env`, `local.secret`, token, key, password를 출력하지 않는다.
