# 똘망이 루프엔지니어링 방법 — SmartReturn Pro

> 매일 따라 하는 작업 루틴 체크리스트는 `ai-harness/SOP-work-routine.md`를 본다.
> 이 문서는 그 배경이 되는 루프엔지니어링 이론·설명이다.

핵심은 "똘망이를 더 똑똑하게 만든다"가 아니라,
똘망이가 반복 작업에서 어디서 흔들리는지 관찰하고
그 흔들림을 규칙·문서·체크리스트·중단조건으로 고정하는 것입니다.

## 1. 먼저 똘망이의 루프를 정의한다

현재 똘망이 작업은 대략 이렇게 돕니다.

- 목표 입력
- AGENTS / memory / handoff / spec 읽기
- 작업 범위 판단
- 구현 또는 검수
- 테스트 / build / diff check
- 보고서 작성
- 커밋 후보 정리
- 사용자 승인 후 커밋 / push

루프엔지니어링은 이 흐름을 매번 새로 지시하지 않고,
"어떤 상황이면 어떤 루프를 탄다"로 고정하는 작업입니다.

## 2. 루프를 종류별로 나눈다

가장 먼저 아래처럼 작업 루프를 분리하면 좋습니다.

- 스펙 루프:
  새 화면/기능 → SPEC 작성 → 사용자 승인 → 구현 대기

- 구현 루프:
  승인된 SPEC → 코드 구현 → build/test → build 보고서

- 검증 루프:
  구현 결과 → 회귀/권한/격리/테스트 검수 → verify 보고서

- 커밋 루프:
  승인된 파일만 선별 add → diff check → commit → status 보고

- 장애 루프:
  테스트 실패 / 권한 누수 / 설계 충돌 / DB 위험 → 멈춤 보고

- 인수 루프:
  사용자가 화면 확인 → 승인 / 보류 / 재작업 결정

## 3. 똘망이를 분석할 때 볼 항목

작업 하나가 끝날 때마다 아래를 기록하면 됩니다.

- 입력이 명확했나?
- 똘망이가 엉뚱한 파일을 읽었나?
- 작업 범위를 벗어났나?
- 중간 보고가 너무 많았나?
- 테스트 실패를 제대로 분류했나?
- 기존 이슈와 신규 회귀를 구분했나?
- git add 범위를 정확히 지켰나?
- 보고서가 다음 작업자가 바로 이어받을 수준이었나?
- 사용자가 반복해서 같은 말을 하게 만들었나?

여기서 반복되는 문제를 "루프 결함"으로 봅니다.

## 4. 루프 결함 예시

예를 들면 이런 것들이 똘망이 루프 결함입니다.

- SPEC 없이 구현을 시작함
- 검수 작업인데 코드를 고치려 함
- 기존 실패 테스트를 신규 회귀로 오판함
- build 보고서가 없는데 있는 것처럼 검증함
- git status가 dirty인데 clean 전제로 진행함
- SmartReturn Pro와 SmartReturn 플랫폼을 혼동함
- 경로를 절대경로처럼 하드코딩함
- 보고서가 길지만 판단이 없음
- 커밋 대상 외 파일이 섞임
- 권한/테넌트 작업에서 DB 실제 상태를 안 봄

## 5. 좋은 똘망이 루프의 형태

좋은 루프는 이렇게 생겼습니다.

- 시작 전:
  AGENTS 확인, status 확인, SPEC 확인

- 작업 중:
  범위 밖이면 멈춤
  작은 오류는 수정
  큰 정책 문제는 사용자에게 반환

- 검증:
  관련 테스트
  build
  git diff --check
  권한/격리 작업이면 DB 실제 상태 확인

- 보고:
  통과 / 부분통과 / 실패
  근거 파일
  미실행 항목
  남은 위험
  커밋 후보

- 커밋:
  사용자 승인 후 선별 add
  git add . 금지
  push 별도 승인

## 6. 똘망이 루프엔지니어링 문서 구조 추천

저장소에는 너무 많은 운영 문서를 만들기보다,
아래 정도만 유지하는 게 좋습니다.

- AGENTS.md
  절대 규칙, 프로젝트 원칙, 보안/권한/DB/검증 규칙

- CLAUDE.md
  Claude Code 전용 작업 방식

- docs/decisions/decision-log.md
  이미 결정한 정책 기록

- docs/decisions/tenancy-and-permission-model.md
  권한/테넌트 북극성

- docs/specs/SPEC-XXX-*.md
  작업 단위 스펙

- docs/reports/SPEC-XXX-build.md
  구현자 보고

- docs/reports/SPEC-XXX-verify.md
  검수자 보고

이 정도면 충분합니다. 문서를 더 늘리는 것보다,
루프가 흔들릴 때 기존 문서에 짧게 보강하는 게 좋습니다.

## 7. 바로 적용할 운영 방식

앞으로 똘망이를 이렇게 쓰면 됩니다.

- 새 화면/기능:
  "먼저 SPEC 작성. 구현 금지."

- Claude 작업:
  "SPEC 기준 구현 + build 보고서 작성."

- Codex 작업:
  "검수·테스트·회귀·권한·diff check. 커밋 금지."

- 커밋 작업:
  "사용자 승인 파일만 선별 add/commit. push 금지."

- 이상 상황:
  "고치지 말고 먼저 보고. 단, 명확한 소수정은 같은 범위에서 허용."

## 8. 핵심 결론

똘망이 루프엔지니어링은
프롬프트를 더 길게 쓰는 일이 아니라,
반복되는 판단을 문서화하고,
반복되는 실수를 중단조건으로 만들고,
반복되는 검증을 체크리스트로 고정하는 일입니다.

즉, 똘망이를 "말 잘 듣는 AI"가 아니라
"작업 흐름을 지키는 팀원"으로 만드는 작업입니다.

## 부록: 루프 개선 방법

반복 결함이 보이면 아래 방식으로 고칩니다.

- 지시문을 길게 하지 말고 루프 문서에 규칙 추가
- "항상 해야 할 것"은 AGENTS.md 또는 memory에 둠
- "작업별로 다른 것"은 SPEC이나 current instruction에 둠
- "검증 기준"은 보고서 템플릿에 둠
- "멈춰야 할 상황"은 중단 조건으로 명시
- "커밋 대상"은 항상 파일 목록으로 고정
- "테스트 실패 분류"는 base-comparison 규칙으로 고정
